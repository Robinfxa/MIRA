### IMGENABLE01-001 Explicit startup choices
Given any combination of the four image enablement/data/subscription/custom-brief flags, when producing startup metadata, then startup_requested records the actual booleans alongside story and API-spend selection, does not synthesize missing consent, mutate CLI arguments or enable a feature from its model, and preserves unknown account access and unobserved provider status.

### IMGENABLE01-002 Executable subscription and voice example
Given the complete command extracted from STORY_IMAGE_OPTIONS.md, when parsed by the real CLI and changed only from serve to check with synthetic speech-only configuration and unread synthetic ADC metadata, then the native Luna mode needs no JEV/API credential, all required explicit image flags are present, and check performs no provider, authentication or voice allocation. It reports configuration only, at most one generation and one pixel read by default, zero retries and no automatic API fallback. This is not a serve, real account, image quality or device acceptance test.

### IMGENABLE01-003 Separate local capability from provider qualification
Given a disabled runtime, missing custom-brief consent, exhausted shared process budget, unobserved provider, or observed image/review port error, when safe readiness is projected, then those facts retain distinct classes. Fixed-photo availability cannot imply dynamic generation; a new session cannot refund process capacity; local decode failure cannot be renamed provider failure. The guide must describe these distinctions without guessing remote account eligibility from local state.
