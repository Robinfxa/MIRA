# 角色／场景驱动与多模态表现：研究汇总与接入建议

**整理日期：2026-10-02**  
**适用范围：72 小时移动端网页互动场景 MVP；保留已有 Memory 与 Live Voice 设计。**  
**文档状态：研究建议，等待接入验证；不是已完成实施报告或稳定性认证。**

## 1. 结论

本轮建议保留为：**优先接入 Charivo 的角色渲染与控制模块，在自己的应用里保留剧情、场景、时间线和打断总控。**

推荐组合：

```text
已有 Memory 与 Live Voice
        ↓
应用自己的 Performance Adapter
        ├── Charivo：角色渲染、表情、动作、视线、口型桥接
        └── 轻量 Scene Runtime：背景、镜头、灯光、道具与媒体事件
```

选择 Charivo 是因为它的模块边界与“已有脑和声音，只缺表现层”的需求匹配，不是因为本轮已经证明它生产稳定。官方文档明确区分渲染器、渲染管理器和可选的 Avatar 工具层。[S1–S3]

**替代路线：Three.js + `@pixiv/three-vrm`。**其公开接口覆盖 VRM 加载、表情、视线和人形骨骼等基础能力，库采用 MIT 许可。[S6–S7] 但它是另一条资产与实现路线，不是临近截止时把一个类名替换掉就能完成的即时备用方案。

**不建议本次整套迁入 AIRI 或 Open-LLM-VTuber。**把它们作为实现参考，而不是重新引入一套对话、语音和会话系统。这是针对当前项目边界的工程取舍，不是对项目质量作总体否定。[S4–S5]

**不把实时生成视频放进核心交付依赖。**LemonSlice 作为商业候选与表现参考；Tolan、Animates、Wan-Streamer、Convai Maya、Covert Protocol 主要提供设计启发。公开演示与实际可集成能力必须分开。[S9–S16]

## 2. 任务依据与证据边界

### 2.1 用户与题目给定的前提

用户表示，记忆与 Live 语音已有较清晰的设计，希望表现层同样出色，并优先复用开源项目或采用可控方案。**这不等于本报告已经审计了这两部分的代码、性能或打断实现。**

上传题目《72 小时实验：实时互动场景产品》要求：

| 题目要求 | 原文件位置 |
|---|---|
| 移动端网页优先，以场景和角色为主体，不以传统聊天列表为主界面；使用原创成年角色 | 第 1 页 |
| 待机、倾听、思考、说话四种可感知状态 | 第 1 页 |
| 至少 3 种可辨认表情／情绪、2 种非说话动作或视觉状态、1 次环境／镜头变化、1 次对话触发的明显视觉事件 | 第 2 页 |
| 打断后停止语音，取消未完成回复及尚未播放的字幕、动作和媒体，阻止旧响应覆盖新状态 | 第 2 页 |
| 至少集成一种角色动画、状态驱动视频、生成图片或生成视频能力；处理相应加载、失败和打断 | 第 3 页 |
| 无私人密钥也能查看核心流程，例如 Mock 或回放；提供可运行闭环 | 第 3 页 |
| 标注服务与素材来源；交付 3–5 分钟演示并展示一次失败／降级 | 第 4–5 页 |

来源：[S0]。Mira 是题目给出的可选故事种子，不是必须采用的人物。

### 2.2 本轮实际完成了什么

重新核对了官方项目 README、接口指南、产品／研究演示页面及许可证说明。没有进行依赖安装、构建、真实通话、移动端压测、商业 API 付费测试，也没有审计用户目标仓库。

- **来源确认**：公开官方文档确实描述了该能力或限制；不等于我们实测通过。
- **推荐设计**：基于当前需求提出的实现边界与取舍；不是框架现成功能。
- **待验证**：必须通过代码检查、真实资产或目标设备测试才能确认。

不将先前回复中的 star 数、版本号或“成熟很多”等概括作为稳定性证据。后续实施需要记录实际锁定的版本、依赖和验证结果。

## 3. 开源候选与推荐角色

| 项目 | 来源确认的定位 | 对本项目的建议 | 不能直接假定的事项 |
|---|---|---|---|
| Charivo | 模块化 TypeScript 角色框架，分离 render、Live2D renderer 和 Avatar 工具层 [S1–S3] | **首选接入候选**，只接表现层 | 自有音频直接兼容、全部动作可取消、移动端稳定、任意动作可生成 |
| AIRI | 支持 Live2D／VRM 的数字陪伴项目，提供 Web 与桌面入口 [S4] | 参考角色容器与交互；不整套迁入 | 内部模块能无改动独立安装、已有记忆／语音可以零成本替换 |
| Open-LLM-VTuber | 包含 Live2D、语音交流与打断的完整项目 [S5] | 参考语音与角色联动、状态处理 | 项目名或使用量等于生产稳定；最新重写版已交付 |
| Three.js + three-vrm | VRM 渲染基础库，提供表情、视线、骨骼等接口 [S6–S7] | 不走 Live2D 时的**独立替代路线** | 自带完整表演导演、成品动作资产、与 Live2D 资产互换 |

补充：Open-LLM-VTuber 当前 README 公告称 v2 在早期讨论与规划，v1 继续修复问题。因此不应把“未来 v2 重写”算作当前可交付能力。[S5]

## 4. 表现出色的案例：借设计，不混淆接入条件

### Tolan：统一的角色设计与动画语言

官方设计文章描述了关键帧、程序动画和状态机的组合，以及后续逆向运动学驱动的程序动画与人工关键帧设计。[S9]

**本项目启发：**状态机并不意味着表现粗糙。Mira 应有自己的动作习惯：倾听时停下整理相机，犹豫时先移开视线，放松时减少防御姿态。将精力投入到少量高质量动作及衔接，而不是堆积情绪标签。

### Animation Inc / Animates：全身表演

官方把 Ani-2 描述为专有的端侧实时全身 3D 动画模型，Animates 是相关角色产品。[S10]

**本项目启发：**把肩膀、躯干、视线与动作收尾纳入表现，而不仅是嘴部。本文不将其视为已经确认可获得的开源 H5 SDK，也没有验证其宣传中的延迟指标。

### LemonSlice CWM-1：角色、动作和环境共同生成

官方发布页介绍了身体、手势、情绪与场景共同参与的实时角色视频；其 WebSocket 文档允许外部 PCM 音频输入，输出同步音视频，并定义播放完成与打断事件。[S11–S12]

**本项目启发：**可把商业 Avatar 服务作为自有脑和声音之外的视觉输出端，但接入会影响音视频播放路径，需要测量新增延迟。公开价格页将 CWM-1／Lite 列在 Ultra 及以上层级，不能用“有便宜套餐”推导“高级模型可低门槛使用”。[S13]

之前提到的手动动作清单，本轮对应页面未成功读取；因此本报告不把任何特定道具动作视为已重新确认。更不承诺其可以按要求递出指定相机或展示指定照片。

### Wan-Streamer v0.3：世界设定与事件流

研究页面将持续世界设定和动作／讲话事件结合，展示实时全双工对话。同时明确将另一组通用物体操作视频标为离线、静音的预训练结果。[S14]

**本项目启发：**让角色原本就在做事情，用户的话改变其行为。不能把离线视频效果当成可实时调用的能力；本文未确认可直接采用的公开服务接入路径。

### Convai Maya 与 Covert Protocol：对话改变环境关系和剧情

Maya 是针对 Quest 3 的混合现实演示，官方介绍了利用房间布局进行导航。Covert Protocol 是 2024 年的 UE5 技术演示，对话结果与任务推进相连。[S15–S16]

**本项目启发：**关键对话应改变角色愿意展示的物件、允许进入的剧情节点或接下来的行动，而不是只换一句回答。两者不作为本次移动网页可直接套用的成品依赖。

## 5. Charivo 的最小接入范围

### 5.1 包边界

```text
优先评估：
  @charivo/render
  @charivo/render-live2d

按需要使用：
  @charivo/avatar   —— 受资源目录约束的工具定义与结果投影
  @charivo/core     —— 公共类型／事件总线等依赖，核对实际需要

不替换已有业务系统：
  LLM、STT、TTS、Realtime 的业务编排
  Memory、剧情事实源、会话身份与打断总控
```

这是建议接入边界，不是经构建验证的最小依赖清单。`@charivo/avatar` 不负责渲染或会话状态；应用自行决定动作时也可使用事件路径，不必强行采用其工具层。[S2] 不接管其完整业务编排，不代表依赖树中绝对不会出现 `core`。

### 5.2 已确认的控制方式

官方 Avatar 指南提供 `setExpression`、`playMotion`、`lookAt` 工具，以及 `avatar:expression`、`avatar:motion`、`avatar:gaze` 事件。表情与动作目录来自已加载模型，并对调用参数做约束。[S2]

**接入要求：**等待资源加载后再发布能力；语义名称如“紧张”“看向窗户”由应用映射到真实资产。`hold_camera`、`show_camera`、`clutch_camera` 等是此前剧情草案中的名字，不是 Charivo 已提供的通用动作。

### 5.3 需要特别检查的框架行为

渲染指南公开了音频开始／结束和口型更新事件；还描述了表情在音频结束时自动释放、视线驱动优先级，以及动作附带音频的静音选项。[S3]

这对我们意味着三个检查点：

1. 外部 Live 的实际播放事件如何映射到框架事件，而不是只转发“生成完成”。
2. 我们希望保留的情绪与框架自动释放逻辑是否冲突；只能有明确的最终写入者。
3. 动作资源里的预录音频不能与当前角色语音同时播放。

此前示意的 `character.clearMotion()`、`audio.stop()`、`scene.camera()` 等不能当作经过核验的 Charivo API。它们表达的是应用应具备的能力，具体取消方法必须检查锁定版本的真实接口。

## 6. 推荐系统设计：保留自己的导演与播放总控

本节是建议设计，尚未实现。

### 6.1 四类状态不要混为一谈

| 状态域 | 示例 | 建议的事实源 |
|---|---|---|
| 交互状态 | idle / listening / thinking / speaking | 自有 Live／播放控制器 |
| 持续情绪 | 戒备、放松、低落 | 应用角色状态 |
| 临时动作 | 看窗外、整理相机、展示物件 | 演出队列与角色适配器 |
| 剧情／世界事实 | 照片是否真的展示过、当前场景 | 自有 Scene State |

进入倾听不应等于清空所有情绪；取消当前回复也不应撤销已经展示给用户的事实。对尚未发生的剧情推进，建议等展示成功后再确认。

### 6.2 画面分层

```text
SceneRoot
├── BackgroundLayer       咖啡馆与窗外
├── EnvironmentLayer      雨、反光与灯光
├── CharacterCanvas       Charivo / 其他角色渲染器
├── PropLayer             相机与照片
├── MediaLayer            剧情图片或短片
├── SubtitleLayer         当前有效字幕
└── Controls              文字、语音、停止与重试
```

建议本次场景层使用现有前端组件、DOM/CSS 与必要的 Canvas，而不是为一个小场景引入完整游戏引擎。角色与环境分层可降低联调范围；这不意味着资产可以省略。

### 6.3 音频只有一个播放权威

保留现有 Live 播放器。表现层消费**角色实际输出音频**的播放进度、开始／结束和必要的口型信号；不要额外启动第二套 TTS，也不要误用用户麦克风驱动角色说话口型。

若采用音量包络控制嘴部，只应称为音频驱动口型近似，不能宣传为音素级精确同步。外部音频能否接入框架既有口型桥，需要验证实际数据格式与调用路径。

### 6.4 演出时间线不要依赖模型猜毫秒数

此前按 `at: 650` 等绝对毫秒排动作，只是概念示意。本次更建议以真实播放开始、已获得的播放位置、动作／媒体就绪等事件驱动；仅在有可靠语音时间戳时做细粒度同步。

不要为等图片、短片或整段演出计划而阻塞第一句声音。所有回调都必须能识别它属于哪次有效回复。

### 6.5 统一打断合同

建议为一次有效输出分配 `sessionId`、`responseId` 与递增的 `epoch`；具体命名按现有 Live 系统调整。

```text
用户打断
  → 先使旧 epoch 失效
  → 本地停止语音播放并清空缓冲
  → 请求上游取消生成（尽力而为，不能作为唯一保障）
  → 取消未执行的字幕、动作、镜头和媒体事件
  → 收住当前可中断动作，回到倾听表现
  → 拒绝所有旧 epoch 的迟到回调
```

验证点不仅是网络请求有没有取消，还包括已经排队的动画回调、图片加载、视频播放、字幕追加和工具调用结果。角色加载与演出事件也要经过应用的有效性检查。

## 7. 素材与剧情：开源框架不会自动补齐的部分

### 7.1 素材先于复杂编排

交付角色需要一份能真正加载并演出的原创成年角色资产，以及明确的使用权。题目样例人物 Mira 的参考描述可以指导美术，但 Charivo 的示例模型不能只改名字就被称为原创 Mira。[S0–S1]

建议先确认：3 种实际可辨认的表情、2 种与说话无关的动作或视觉状态、待机／倾听／思考／说话的表现方法、统一风格的背景与剧情物件。

“模型支持播放动作”不等于“任何模型都有我们需要的动作”。看窗外、抱紧相机、递出照片分别需要对应资产或经过验证的场景演出替代。未验证的动作不应出现在对模型公开的能力目录中。

### 7.2 推荐保留的四个剧情节拍

以下是上一轮方案的整理，属于创作草案：

| 节拍 | 对话条件 | 视觉反馈 | 注意事项 |
|---|---|---|---|
| 相遇 | 普通寒暄 | 停下手头小动作、转向用户 | 用倾听建立注意力，而不是频繁大动作 |
| 触及秘密 | 谈到等待、打烊或不愿离开的原因 | 移开视线、改变姿态 | 不依赖固定倒计时推进 |
| 展示物件 | 谈到摄影／相机，且剧情允许展示 | 镜头关注道具，显示照片 | 没有递相机资产时，改用已验证的物件特写 |
| 回应照片 | 用户询问照片内容 | 表情变化、视线回落、环境配合 | 对话使用同一份照片事实，不凭空换故事 |

建议 MVP 使用预先确定的剧情照片。后续再尝试动态生成；生成结果必须与剧情事实保持一致，失败时不得让角色声称已展示不存在的图片。

### 7.3 稳定降级与合格交付不同

角色渲染失败时显示静态参考图，可以作为降级体验，但不自动意味着“3 表情、2 动作、多模态能力”等正常路径要求已经满足。正式演示仍需展示实际成功路径与一次有标识的降级。[S0]

## 8. 接入验证与停止条件

详细清单见 `integration-checklist.md`。本轮所有执行项均为**未执行**。

建议实施顺序为：**资产与许可确认 → 锁定依赖 → 单角色显示与动作 → 接自有音频 → 统一打断 → 场景事件 → 真机与无密钥演示。**

| 验证关口 | 必须拿到的证据 |
|---|---|
| 资产可用 | 原创与使用权说明；实际播放所有需要的表情和动作 |
| 最小渲染 | 能在目标网页构建中加载，无多余语音／会话系统 |
| 音频桥接 | 只有一个音源；嘴部跟随实际播放；结束和打断均能停 |
| 取消能力 | 正在说话／做动作／加载媒体时打断；旧回调不会恢复 |
| 剧情因果 | 有一次由当前对话触发的可观察视觉事件 |
| 目标设备 | 记录实际设备、浏览器、加载时间和连续会话表现 |
| 公开演示 | 无私人密钥也能走核心流程；失败状态可恢复 |

如果核心动作无法取消、原有 Live 无法桥接，或无法获得合格素材，不应继续向上堆剧情功能。先选择更薄的渲染接法或重新选择角色路线，并保留当前未通过的验证记录。

不作“72 小时一定能完成”或“第二天可以无损切换 VRM”的保证。适配器减少的是业务耦合，不能消除 Live2D 与 VRM 的资产、动画、坐标和表现差异。

## 9. 许可证与发布边界

Charivo README 说明：多数包为 MIT，但 `render-live2d` 涉及 Cubism 的独立许可；示例模型又是另一层素材许可。[S1]

Live2D 官方区分开发验证与发布，并对 Expandable Applications 单列规则。[S8] 本报告不判断用户是否符合豁免，也不承诺公开演示天然不需要处理许可。应分别记录代码、SDK、模型、动作、背景和音效来源。

Three-vrm 的 MIT 只说明库代码许可，不替代角色模型、贴图和动作的授权。[S7]

## 10. 对之前建议的明确收紧

| 之前容易被理解为 | 本次准确结论 |
|---|---|
| “Charivo 是已证明稳定的 72h 方案” | Charivo 是适配当前边界的首选候选；稳定性必须由我们的接入测试证明 |
| “只装三个包就肯定够” | render + render-live2d 为核心；avatar 可选，core／事件依赖需核实 |
| “`clearMotion()` 是现成 API” | 之前是应用能力示意；取消方法尚需源代码／接口验证 |
| “有渲染器就有 Mira 的所有动作” | 表演能力取决于实际模型与动作资产 |
| “打断时恢复默认脸就完成了” | 交互状态与持续情绪分开管理；避免自动表情释放与应用策略互相覆盖 |
| “接口隔离意味着 Live2D 与 VRM 一天内互换” | 只能减少业务改动，不能消除资产与动画迁移 |
| “star 多或版本新就稳定” | 本报告不以这些数字作为稳定性证明 |

## 11. 可直接交给开发 Agent 的任务摘要

> 在不替换已有 Memory 与 Live Voice 的前提下，优先验证 Charivo 的 render／render-live2d 模块与可选 Avatar 工具层。先检查现有前端、音频播放权威、打断机制和角色资产，再确认所需依赖与取消接口。让一个原创成年角色完成可辨认表情、非说话动作、自有音频口型桥接，以及一次对话触发的场景事件。所有输出归属同一有效回复标识，打断后旧字幕、动作和媒体回调不得恢复。保留 Mock／回放与失败降级。只报告实测结果，不把 README 能力、示例 API 或本报告建议当成已完成实现。若无法满足关键关口，先回报具体缺口，不自行扩大为全新语音系统或完整游戏平台。

**最终推荐：保留已有脑与声音，优先借 Charivo 做角色，自己掌握场景与打断；用资产质量和端到端验证保证表现，不用框架名替代验收。**
