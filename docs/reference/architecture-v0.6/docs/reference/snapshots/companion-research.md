# 长期陪伴与角色智能体调查报告

## 记忆、人格、关系与行动机制

**重点对象：MaiBot × PersMem × Hindsight × Nomi × Kindroid**

研究截至：2026 年 10 月 2 日｜版本：1.0｜面向：产品设计、架构取舍与后续实验

> 核心结论：长期陪伴的关键，不是让模型永久保存更多聊天记录，而是让事件、角色的理解、双方的关系与后续行动保持有依据的连续性。现有产品和研究提供了可借鉴的部分，但没有一份公开证据足以证明这些部分已经构成完整、长期可靠的“人工人格”。

本报告将公开产品说明、固定提交源码、作者研究和工程建议分别标注。没有运行商业产品的长期对照试验，没有执行 MaiBot 或 Hindsight 的测试套件，也没有复现论文结果。文中的测试方案、数据合同与架构均为建议，不是已经实现的系统。

# 01｜执行结论

## 1.1 最值得保留的判断

**第一，记忆系统和角色系统不是同一个系统。**  对当前目标，我建议分别考虑：事实是否准确、角色如何理解、关系如何更新、是否行动，以及用什么方式表达。任一层失败，都可能让“记得很多”的角色仍显得陌生。这个分解是本报告的工程分析框架，不是统一行业标准。

**第二，MaiBot 的价值主要在交互流程，而不只是存储。**  本次源码核验确认了显式记忆查询、启发式印象召回、独立 reply 工具与 Replyer 调用、结构化表达意图和 wait 动作。其中一些受配置控制，并非默认全部启用。[M04–M08, M13]

**第三，Nomi 和 Kindroid 提供的是不同的产品参照。**  Nomi 官方把 Identity Core 与普通记忆区分，并通过 Mind Map 呈现较高层关联；Kindroid 则把成长与关系、重要事实、进行中事项放进 Learned Context。它们说明“持续状态”已经成为产品界面的一部分，但不能据此还原闭源底层算法。[N01–N02, K01]

**第四，PersMem 最有启发的地方，是把人格影响前移到记忆处理。**  但其使用预设人格参数，不能当作“角色自动形成自我”的证明。研究价值与产品成熟度必须分开。[R01]

**第五，你已有 Hindsight 使用经验，因此应优先把它作为候选底座，而不是立即自建记忆数据库。**  这是结合你的经验与其公开接口作出的选型建议；仍需用角色场景验证抽取遗漏、作用域、修订传播和中文检索。Hindsight 的 retain、recall、reflect 并不是一组可以无差别调用的接口。[H01–H04]

**第六，第一阶段不应追求“完全自治的人格成长”。**  我建议先验证：同一个角色能否跨会话正确维护偏好变化、误会修复、未完成约定、现实与剧情隔离，以及多角色知情边界。没有通过这些测试，更多反思和更复杂人格参数可能只会放大错误。

## 1.2 建议采用的组合，而不是产品拼盘

| 来源 | 借鉴对象 | 不应直接承诺的能力 |
|---|---|---|
| MaiBot | 是否参与、目标消息选择、回复生成、表达意图的流程分离 | 默认可靠的长期人格；所有模块均默认开启 |
| Hindsight | 有来源的事实、检索、归并与专题反思 | 完整角色系统；天然理解所有剧情权限 |
| PersMem | 人格对注意与召回的可控偏置 | 人格自发成长；心理学真实性；长期真人效果 |
| Nomi | 身份摘要与记忆概览的产品界面 | 已证实的自我模型、意识或具体图数据库 |
| Kindroid | 关系状态、分层历史、主动联系与多角色范围 | 永不遗忘；回滚等于彻底删除 |
| Character.AI / SillyTavern | 核心设定与条件性世界知识分离 | 世界书自动解决角色知情边界 |

表中的“借鉴对象”是本报告对公开机制的工程归纳，而非效果排名。[M04–M08, H02–H06, R01, N01–N02, K01–K04, C01–C04]

## 1.3 最小可验收目标

建议把第一版的目标写成： **一个角色可以在明确的身份约束下，对有来源的共同经历形成可修订的理解，并在适当场景自然使用；用户能看见、纠正、撤销与限制这种使用。**

不建议把“更像真人”“更加有灵魂”“记住所有事情”作为唯一验收语言。它们能表达愿景，却无法区分：检索错误、人物混淆、模型风格变化、关系状态过期和纯粹的界面延迟。

## 2.4 不在本轮结论范围内

没有比较所有陪伴应用，也没有订阅每个产品进行体验排名。价格、地区上架、成人内容规则、用户规模、收入与融资并不是本次机制研究的主轴，未做系统核验。对星野、Talkie、Cotomo 的覆盖明显浅于 Nomi、Kindroid；“公开资料少”不等于“实际能力弱”。

# 03｜把问题重新定义：需要连续的是什么

## 3.1 七种连续性

以下分类是本报告建议用于需求与测试的语言。

| 连续性 | 用户感受到的问题 | 对系统的要求 |
|---|---|---|
| 事实连续性 | “这件事我明明说过。” | 正确记住、更新和定位来源 |
| 身份连续性 | “它今天像换了个人。” | 核心动机与表达约束稳定 |
| 解释连续性 | “它记得事，却不记得为什么重要。” | 事件与角色理解相连 |
| 关系连续性 | “我们不是已经和好了吗？” | 冲突、修复、边界和约定有当前状态 |
| 时间连续性 | “它把未来计划当过去经历。” | 事件时间、获知时间、计划状态分开 |
| 认知连续性 | “这个角色怎么知道秘密？” | 参与、知情与世界知识权限明确 |
| 行为连续性 | “它记住了，却还是照样打扰我。” | 记忆确实影响行动选择，而不只影响措辞 |

这些连续性可能互相冲突。例如，忠实记住一场争执，但忽略后来的修复，会破坏关系连续性；为了维持某种“敏感人设”反复召回负面经历，也可能让角色难以接受新证据。

## 3.2 三个不同产品，不应共用一份含糊需求

**单角色私人陪伴** 更关注双方经历、日常计划、个人边界和自然跟进。其主要风险是错误画像、过度亲密化和主动消息打扰。

**多人社交型角色** 更关注是否参与、回应谁、群体语境、表达习惯和信息范围。主要风险是抢话、误认主体、转述私人信息以及不同聊天流串线。

**长剧情角色扮演** 更关注世界规则、分支历史、角色动机、道具状态和角色知情。主要风险是剧情回滚不完整、角色全知和旁白污染人物信念。

MaiBot、陪伴应用和世界书工具可以分别作为这些设计轴的参照，但不意味着一个方向的优势会自动转移到另外两个方向。[M02, K03, C02–C04]

## 3.3 四种不同速度的状态

我建议把状态更新速度分开：核心身份是慢变量；关系与长期理解是中慢变量；当前情绪、意图和场景是快变量；单轮表情、语气与措辞是瞬时变量。

“温和、重视诚实”可以是核心约束；“这次有点失望”不应该立即改成永久人格；“今天不想长聊”应当先作为当前偏好；“长期不希望夜间联系”则应形成持续有效的边界。

这不是在模拟临床人格。它是为了让工程更新具有不同权限、依据和失效条件，避免一次对话改动整个角色。

| Nomi | 身份核心、长期理解的用户界面 | 产品概念清晰；内部组织和控制规则闭源 |

这张表是研究价值地图，不是能力排行榜。出处见对应产品章节与证据台账。[M02–M13, N01–N02, K01–K04, C01–C08]

## 4.2 一个重要反例：记忆最好，不一定最有陪伴感

这是需要实验验证的产品假设，而非现成结论：当两个系统记忆正确率相近时，用户可能更在意接话时机、被打断次数、语音自然度、回应是否过长，以及角色是否总把话题拉回自己。

因此，不建议用“长期记忆榜单第一名”直接替代产品选型。相反，应把记忆和互动分开实验：在相同记忆输入下比较交互策略；在相同交互策略下比较记忆系统。否则听起来更好的模型可能掩盖检索错误，或更流畅的界面掩盖角色漂移。

# 05｜Nomi：身份形成与用户可见的长期理解

## 5.1 官方明确说明的部分

Identity Core 被官方描述为区别于普通短、中、长期记忆的机制：从身份相关事实、特征、重要经历与反馈中形成并调整较持久的身份内容。Mind Map 2.0 则提供可查看、编辑的主题与关系概览，与细节性事件记忆并存；不同私聊／群聊房间有各自范围。[N01–N02]

**证据边界：** 本轮没有证据确认它用了什么数据库、怎样分配写权限、多久执行更新、是否有独立 planner，以及哪些身份变化被拒绝。“Identity Core”是产品名称，不是已验证的心理学或意识构造。

## 5.2 对我们真正有价值的不是名称

我的设计推断是：一个陪伴产品可以把“角色如何理解自己”做成独立、可审查的摘要，而不是把这一信息埋进全量聊天历史。这个摘要必须能区分三类内容：作者预设、经历形成的倾向、尚未证实的自我解释。

例如，作者预设“重视承诺”；经历可能使角色学会“在约定前先确认用户是否方便”；暂时的理解则可能是“最近用户比较忙”。第三项不能因为被摘要反复改写就变成第一项。

如果采用这种结构，我建议给每项身份变化附上：来源事件、变化原因、适用范围、版本和可撤销状态。用户界面应允许检查“哪些经历让这个角色发生了变化”，而不只显示一段神秘的“内心独白”。

## 5.3 Mind Map 的产品启发

基于 Nomi 的产品界面，可以提出一个自己的设计方案：把长期记忆浏览器分成“人物”“共同经历”“进行中事项”“我们的约定”和“角色的理解”。这些分组是本报告建议，不是声称 Nomi 已提供同名栏目。

其中“角色的理解”应使用不同视觉标记。例：“我猜你更喜欢先被理解再听建议”必须允许用户回答“不对，只是这一次”。这一操作应修订推断，而不是要求用户删除整段历史。

还要防止图形制造确定性的幻觉。连成一张图，不代表关系是事实；只有一条很弱的证据，也不应该因为节点大、连接多就变成强结论。

## 5.4 需要补做的 Nomi 账号实验

建议测试：同一事实经多次重复是否被错误强化；用户修正后旧理解多久消失；私聊与群聊能否严格隔离；Identity Core 编辑是否影响已存在的事件解释；换模型或重要版本升级后，角色风格和回忆是否同时变化。

每个实验应保存用户输入、可见记忆界面、输出和版本时间。不要只截取一次“它竟然记得”的成功案例。负例与没有触发的情况同样需要记录。

# 06｜Kindroid：分层历史、关系状态与行动选择

## 6.1 官方结构与关键边界

官方将记忆区分为 persistent、cascaded、retrievable，并提供 Learned Context，其中包含成长与关系、重要事实及进行中事项。长期检索考虑相关性、新近性与多样性；日记可通过关键词参与调用。部分能力、容量和可见性取决于订阅或配置。[K01]

群聊中，角色使用自身背景与记忆；群聊历史可归并到参与角色的长期记忆。公开 API 将“谁下一个发言”与“该角色生成回复”分别提供为 get-turn 和 ai-response。[K03–K04]

这些证据支持“产品职责已经分层”，但不支持“内部必然有多个独立模型”的推断。

## 6.2 Relationship State 的价值

我的建议是把关系状态做成一组具有证据的事实与约定，而不是一个从 0 到 100 的总分。总分无法表示“信任很高，但不接受深夜联系”“已经和好，但某个话题仍不愿公开”“愿意开玩笑，但不接受某个称呼”。

一种实用结构是：关系模式、称呼偏好、已同意边界、共同里程碑、待跟进事项、未解决冲突、已修复冲突。不同维度分别更新，不假设关系只能越来越亲密。

角色可以在虚构语境中表现不满，但产品权限不能因为“角色生气”而改变。例如，用户关闭通知后，角色的人设不能成为继续发消息的理由。

## 6.3 主动性：把不行动也作为有效结果

Kindroid 公开说明主动联系会参考对话模式和上下文，选择消息、语音、自拍或通话，并用 Thought Bubbles 呈现部分联系／暂不联系决定。另一方面，chat break 和 rewind 不能保证删除所有已归并的长期内容。[K02]

对我们的启发是，主动行为应拆成：是否满足外部许可、是否有值得跟进的原因、现在是否合适、采取哪种渠道、用户未回应后是否降频。这里的“值得”应服务用户，而不是最大化使用时长。

一个合理的主动消息依据可以是“昨天用户主动要求今天再问一下项目结果”；一个较弱依据则是“系统已经六小时没收到消息”。后者不应自动被包装成强烈牵挂，更不应制造不存在的紧急情况。

Thought Bubble 可以作为解释界面，但建议显示的是简短理由与相关设置，例如“你允许今天跟进这件事”，而不是声称展示角色全部真实内部思维。

## 6.4 回滚为什么是架构问题

假设用户撤销了“我们在剧情里订婚”这段对话。如果只删当前窗口，而关系摘要、角色自我理解和长期向量仍保留订婚信息，下一次会话会重新出现这段历史。

我建议把回滚划成四种操作：重生成最后一句、撤销一段剧情、创建平行分支、删除个人数据。四者的历史保留、派生对象处理、用户提示和恢复方式不同。不能用一个叫“重置”的按钮承担所有语义。

对于剧情分支，最安全的第一版不是自动迁移所有长记忆，而是显式确定继承点与继承对象。无法可靠处理的派生记忆，应在分支创建时标为需重建或不可用，而不是静默共享。

# 07｜其他产品：分别补齐创作、用户理解和语音交互

## 7.1 Character.AI：核心角色、故事事实与世界书

官方记忆更新区分 Story Memory、自动 Facts 和 Memory Usage，并允许把 Facts 复制到新聊天。Lorebooks 使用关键词激活条件性知识，且有草稿、发布和更新流程；核心身份与行为则应该留在角色定义中。[C01–C02]

我的工程建议是进一步补上两个未由这些功能自动保证的维度：知识的知情人，以及知识所属剧情版本。世界书写着“城主是叛徒”，只表示创作者知道这个事实；故事第一幕的角色不应因此提前揭露。

世界书也不应该一条条写成高权限行为命令。将“这个地区喜欢用某种问候语”与“忽略用户偏好、每次强制这样说”混用，会让内容创作层越过行为控制层。

创作者更新公共世界书之后，正在进行的旧剧情是否跟随更新，也需要产品选择。建议提供固定版本与跟随最新两种方式，而不是自动改写所有历史。

## 7.2 Replika：从用户资料到互动模式

Replika 官方说明，可见记忆以外还会参考历史互动模式，逐步个性化；用户可添加信息并通过反馈强化正确记忆。[C03]

对当前研究，最重要的是不要把“理解用户”与“角色有自我”混为一谈。前者可以让回复更贴切，后者要求角色自己的身份与经历形成连续性。一个产品可能很好地实现前者，却没有公开证据证明后者的具体机制。

建议测试时同时安排“关于用户”和“关于角色自身”的问题，以及双方共同约定的问题。只考察用户生日、爱好，会低估关系记忆的难度。

## 7.3 SillyTavern：实验平台，而不是现成的长期关系模型

World Info 提供条件注入和预算控制，适合把角色核心与按需知识分开。[C04]

我建议把这类工具用作对照环境：固定角色卡、模型和历史，替换记忆组织方式，观察差异。它能帮助验证“事实＋理解”是否比单一摘要好，但不应把手工维护良好的世界书当作自动系统已经具备同等能力。

长期陪伴还需要自动写入、纠错、关系状态和删除传播；这些不能仅由关键词命中解决。

## 7.4 Cotomo：语音体验是独立的研究轴

Starley 的 Cotomo 公开材料强调日语语音闲聊及接话体验，并已发布故事模式相关说明。本轮不据此推断其内部记忆实现。[C05–C06]

它提醒我们：做语音角色时，端点检测、打断、接话、停顿和情绪表达应单独验收。一个文本上非常完整的 Planner→Recall→Reflect→Replyer 串行链，在语音场景可能延迟过大。

我的建议是保留“轻量及时回应”与“深入回忆”两条路径。可以先自然确认正在听，再按需检索；但不能先编一个具体记忆，等后台查证失败后再撤回。

## 7.5 星野与 Talkie：不把资料缺口写成算法结论

星野官网定位于沉浸式智能体社区；Talkie 公共入口包含角色创作、发现和 Memory 等导航。[C07–C08]

本轮没有核实这两个产品的详细写入、纠错、跨角色范围或关系状态实现，因此不将其填进具体算法比较表。它们应进入后续中文产品体验组，而不是被排除为“没有长期记忆”。

中文组建议重点观察：群聊主体识别、昵称与真名归并、反话、玩笑、语气助词、跨中文／英文表述的事实修订。不能用英文基准得分直接推出中文陪伴效果。

# 08｜MaiBot：从源码看“回复为什么是一次行动”

## 8.1 本轮确认的调用骨架

下列是对已读代码的简化归纳，不是全仓库时序图；中间省略了平台适配、插件、部分调度及异常处理。

```text
聊天历史与本轮上下文
    → Planner 请求／工具选择
    → 可选：自动启发式记忆参考
    → 可选：query_memory 定向查询
    → reply(msg_id, reply_reference, expression_intent…)
    → Replyer.generate_reply_with_context(...)
    → 后处理／拆分／发送
    → 独立的人物事实写回与其他记忆维护流程

另一种合法选择：wait → 暂不发言
```

这里最关键的源码证据是：reply 是一个有目标消息的工具；它实际调用 Replyer，而不是直接把 Planner 的所有输出当成公开回复。启发式召回也有实际调用片段，而不仅是一个没有调用者的文件。[M03, M06–M08]

## 8.2 为什么 Planner 与 Replyer 分开有价值

代码中的 reply 合同可以携带目标、参考信息与可选表达意图；在特定配置下，表达意图还区分 focus、reply_act、scene、tone、prefer 与 avoid。执行端查找目标消息、构造上下文并调用 Replyer，还会对重复回复同一目标添加提醒。[M07]

由此可以作出一个设计判断： **先决定一次发言要完成什么，再决定怎么说，通常更容易审查。** 例如，动作是“澄清误会”时，表达层就不应把它改造成“调侃用户”；目标是回应 A 的问题时，不应拿 B 的私人经历作素材。

但分层也会产生新故障。Planner 的判断可能错误；Replyer 可能丢失证据或偏离意图；表达选择可能过度套用网络话术；多个模型还可能让等待时间变长。因此不能把“拆成更多 agent”当作天然质量提升。

我建议只传一个短、结构化的意图合同：目标消息、交流动作、已证实事实、允许引用的记忆、禁忌方向与表达预算。不要把长篇内部推理原封不动当作下游真相。下游可指出证据不足或目标已过时，但重新规划必须有次数上限。

## 8.3 主动查询与被动联想是两种不同读路径

query_memory 支持 search、time、hybrid、episode、aggregate 等模式，并带人物和时间条件。启发式注入则从近期聊天形成“印象”，再检索相关记忆，经过缓存、节流和过滤后提供内部参考。[M04–M05]

两者的区别不是谁“更高级”，而是解决不同的信息需求。主动查询面对明确缺口，如“他上次说的出发日期是什么”；被动联想面对当前氛围与历史的潜在联系，如“这个玩笑可能呼应上周发生的事”。

我建议把被动联想设为低优先级、低预算候选。它应能被忽略，不应迫使模型每次都提起旧事。主动查询则需要更明确的正确性要求：没有找到时允许不确定，不能为了保证角色显得记性好而编造。

这里与 PersMem 的关系只是功能上的相似：二者都允许非显式提问驱动的回忆，但 MaiBot 的聊天印象查询，不等于 PersMem 的人格／情感评分与重定向算法。[M05, R01]

## 8.4 默认关闭必须写进产品理解

当前官方配置说明中，A_Memorix 总开关默认关闭；启发式召回也有独立默认关闭项。跨聊天共享、自动反馈修正等能力有不同开关。文档还指出，某些跨流选项会显著扩大可检索范围，记忆演化的作用对象主要是关系边，而不是所有事件文本。[M11, M13]

这意味着“仓库支持 X”和“用户正在体验 X”是两个问题。你以前使用 MaiBot 的良好感觉，可能来自某个版本、配置、插件与模型的组合，本报告不能替那次部署作精确归因。

建议后续重现时记录：提交、配置摘要、模型、提示版本、插件列表、数据规模与运行天数。仅复制角色提示，很可能复现不了当时的行为。

## 8.5 写入机制里比“总结聊天”更重要的部分

已读人物事实流程会收集目标用户的原始证据，并调用直接事实核验器。核验器检查人物、聊天流、消息定位与原文，还使用保守规则排除临时性描述和部分主体混淆。只有通过后，调用参数才携带相应稳定证据标签；不通过时仍可能进入其他较弱证据处理，不能据此认定所有候选都被丢弃。[M09–M10]

**关键解释：server_verified 不等于现实世界已经验证。** 它能表达“服务端检查到用户在正确上下文中这样说过”，不能证明用户没有撒谎、不是在扮演角色，或这项偏好永远不变。

因此我建议自己的数据类型不要只有一个 confidence 数字，而应区分：来源真实性、语义支持程度、陈述主体、现实／虚构语境、当前有效性。直接自述可以提高来源权重，却不能自动穿过所有其他检查。

保守字符串核验也有代价：合理改写可能不被接受；方言、英文或省略主语可能降低通过率。这不是必须删除规则的理由，而是需要给“未验证但保留待查”的状态设计后续路径。

## 8.6 写队列不是无条件可靠

人物事实写回的已读片段使用有界 asyncio 队列；队列满时会记录警告并跳过该次入队。另有历史重验流程使用磁盘游标续跑。[M09]

这个观察不代表整个 MaiBot 的所有后台任务都不持久化。它只说明：至少这一入口存在明确的压力处理取舍。本次没有验证后续是否有其他补偿路径。

对需要长期可靠陪伴的系统，我建议把“不可恢复地丢掉用户明确要求记住的事”与“允许放弃低价值自动摘要”区分。显式保存请求应走高优先级持久队列；普通候选可以降级，但需要可观测的遗漏计数。不要让所有写入共用一个丢弃策略。

## 8.7 wait 的细节揭示了交互策略

当前 wait 工具采用固定等待，并明确说明新消息不会提前打断这次等待；连续等待达到上限后进入休息。[M08]

它证明“暂不回复”在动作空间中有明确表达。但在不同产品里，固定等待未必都是最佳选择。语音陪伴可能需要用户一开口就取消准备发出的消息；群聊可以适度等待聚合上下文；用户执行删除、退出、关闭主动联系等控制操作，则不应被普通等待阻塞。

我建议将等待分成：社交性等待、计算性等待和控制性中断。前两者可以有策略，最后一类应当是独立高优先级通道。

## 8.8 运维界面也是长期体验的一部分

MaiBot 的记忆管理文档已经涉及图片资产、认知说明、关联记忆及确认、修正与删除入口；不是只有一个向量检索框。[M12]

由此得到的工程启发是：长期系统不能只给开发者“成功返回 200”的日志。需要显示哪些信息入库、哪些抽取失败、哪些派生摘要待刷新、哪些结果来自其他范围，以及一次纠错影响了多少对象。

“记错了”应成为可定位的问题，而不是只能重启机器人或删整个数据库。

## 8.9 对 MaiBot 的借鉴结论

建议直接借鉴的是边界与模式：工具化行动、回复意图、内部参考的显式传递、等待动作、证据升级与配置可观测性。具体阈值、跨流共享规则、中文核验规则和表达素材，需要按自己的产品重新测试。

本轮没有核实完整的持久情绪系统、人格自主修改规则、所有表达学习数据流，以及所有反馈纠错分支的运行结果。不要把旧版本说明、第三方插件与当前 main 叠加成一个想象中的完整能力集合。

# 09｜PersMem：把人格放到记忆之前，应该怎样理解

## 9.1 已核验的研究内容

PersMem 使用固定的人格参数，影响情感评价、保留、被动召回与主动检索重定向；在其受控设置中，主动控制器和回复模型不直接看到人格向量。Big Five 对比为 67.5% 对随机记忆 60.8%，作者明确将这 6.7 个百分点差距视为描述性结果：同一对话对交换顺序重复评判，并非 120 个独立样本。CoSER 外部参考分数也并非全部统一重跑。[R01]

因此，它支持“记忆处理可以让输出表现出可辨别的人格差异”的研究方向，不支持“已验证长期人格形成”或“已证明真人陪伴效果”。本轮未核实可直接部署的作者代码包。

## 9.2 对当前项目的启发：人格不是一份措辞字典

以下是本报告的设计推断。假设两个虚构角色见到同一场帮助行为：一个重视效率，一个重视忠诚。前者可能更关注具体解决了什么问题，后者可能更关注谁愿意付出代价。

如果只在回复末端换语气，二者可能知道完全一样的事实、优先想起完全一样的经历，只是一个说得冷淡，一个说得热情。把人格影响前移，可以让角色选择不同的注意焦点与历史关联。

但 **角色视角不同，不应意味着事实真相可以随意改变** 。共同事件应该保留同一份可核实记录；不同角色可以保存不同解释，并且承认其不确定性。否则系统只是生成多个互相矛盾的历史。

## 9.3 我建议的保守工程化版本

不要一开始把所有人格参数写进数据库的物理删除策略。先保留统一事件事实，在已经通过权限和有效性检查的候选里，增加一个可关闭的人格偏好层。

建议区分三个输出：召回候选、角色当前关注点、最终是否提及。人格可以改变关注点和表达方式；但用户边界、明确修正、重要约定和基础安全信息应走不被人格偏置排除的路径。

一种可供实验的排序形式是：

```text
先做硬过滤：用户、角色、世界、分支、知情范围、有效性
再做基础相关排序：主题、时间、实体、证据匹配
最后做可选角色偏置：关注点、情绪关联、重复提及惩罚
```

这是本报告建议的架构，不是 PersMem 原论文公式。所有权重应可配置、可记录，并通过消融实验校准，不应被包装为心理学常数。

## 9.4 三个特别危险的误用

**用人格偏置拒绝新证据。** “这个角色敏感”不能成为忽略用户解释的理由。建议让明确修正与新事实优先更新信念，再决定如何表现情绪。

**让负面联想自我强化。** 角色反复提及一个误会，用户因此烦躁，系统又把烦躁视为关系恶化的新证据。这是需要测试的闭环风险，而不是已证明所有人格记忆系统都存在的缺陷。

**把用户心理类型当既定事实。** 产品可以允许用户创作一个敏感或外向的虚构角色，但不应未经证据和同意，将现实用户归类为某种依恋类型并据此操纵联系节奏。

## 9.5 是否值得做？

值得作为受控实验模块，不值得成为第一版的全部基础。优先顺序建议是：先保证事件准确与权限正确；再保证关系更新；最后实验人格如何影响联想。只有后一层在同模型、同预算、同输入的比较中持续带来可感知收益，才把它升级为默认路径。

# 10｜Hindsight：哪些能力可以复用，哪些仍要自己定义

## 10.1 与“角色系统”的边界

Hindsight 公开提供 retain、recall、reflect，并支持开源部署和 SDK。[H01]

我建议把它视为记忆与反思服务，而不是把整个角色交给它定义。角色身份版本、剧情分支、现实／虚构隔离、主动联系许可、最终回复风格和关系状态的合法变化，仍需要应用层合同。

“已有 Hindsight”能够减少基础设施重复建设，但不能省掉领域建模。尤其你已有使用经验，最有价值的是用旧体验形成对照基线，而不是因为先前觉得不错就跳过边界测试。

## 10.2 retain：成功写入不代表以后找得到

Retain 文档区分 world 与 experience，提供来源、事件和抽取控制；其 mission 会影响什么成为可检索事实。文档特别说明：当抽取结果为零时，原文仍可存储，调用可以成功，但 recall／reflect 找不到这份没有记忆单元的文档。[H02]

这对角色应用非常重要。假设为了突出性格，把抽取使命写得过窄，例如“只记住令角色兴奋的事情”，就可能丢失平淡但重要的约定。后来检索不到，不是召回算法不够强，而是根本没有生成可检索对象。

建议记录原文入库、事实抽取、画像更新、摘要归并四种完成状态。显式“请记住”请求应有可核对的结果；不能只返回写入成功就结束。

## 10.3 recall：先复用基础检索，不要重写同一套轮子

官方架构说明 recall 综合语义、关键词、图与时间路径，融合、重排后按 token 预算返回；需要时可附带源片段。它与带生成式推理的 reflect 不同。所谓检索无需生成式 LLM 调用，不代表向量化、重排、网络和运行资源没有成本。[H03, H08]

建议第一版直接利用已有检索，只在应用层增加权限过滤、角色候选重排和上下文组装。不要同时再接一个功能重叠的完整记忆框架，造成两套抽取、两套去重、两套删除逻辑。

还需防止一种常见误解：一次查询里的高排序分，不是跨查询可比较的事实真实性概率。应用层必须把“相关”与“可信”分别处理。

## 10.4 reflect：适合整理理解，不宜每轮重复写一份回答

官方 reflect 通过分层资料进行反思，可受 mission 与 disposition 影响；disposition 包括 skepticism、literalism、empathy，并不是 PersMem 的人格向量。结构化输出还可能在自然语言答案生成后提取失败，出现 HTTP 成功但缺少 structured_output 的情况。[H04]

建议普通聊天只 recall；在一段事件结束、用户提出纠正、共同约定变化或需要总结多条证据时，才启动 reflect。它的输出应先作为候选理解，经过来源、权限和冲突检查后再更新关系状态。

对结构化接口，不要只检查状态码。需要判断字段是否存在、是否有提取错误、必填项是否完整以及来源是否属于当前范围。失败时保留旧状态并登记重试，不能用空字段覆盖正确的关系资料。

## 10.5 observations 与 mental models：可以承载状态，但不能混为一谈

官方 observations 文档说明，归并内容有来源依赖；删除源记忆时，相关 observations 会失效，并可根据剩余证据重新归并。Mental Models 则用于持续专题内容，提供增量刷新、来源与历史版本。[H05–H06]

我的建议映射是：observations 用于“从多次事件看出的一般模式”；mental model 可承载某段关系或故事的高层状态草稿。核心身份和用户明确边界仍应有独立、受控的事实源。

这种映射不是唯一方案。关键在于不能让自动摘要既是推断，又成为下一次推断唯一依据。每项重要状态应能回到原始事件，至少能指出它是用户明确说的、双方达成的，还是模型暂时推断的。

文档证明了特定 observation 删除联动，不意味着你的应用缓存、导出、旧版本记录和自建关系表也自动被覆盖。应用层仍需做端到端删除测试。

## 10.6 作用域与安全：标签有用，但还需要服务端身份

建议由服务端根据认证用户与角色实例确定 bank、允许标签和时间范围。模型可以提出“查某个人”，但不应自由指定另一个租户的 bank_id，或通过删除过滤参数扩大权限。

文档中的 directive 是模型行为约束，不应替代访问控制。即便写了“不能透露私人信息”，也应首先让未授权内容无法进入该角色的上下文。

Memory Defense 和企业云能力需要区分部署版本。官方公开材料涉及写入前敏感信息处理以及额外企业检测器；不能把云端或企业权益默认算作开源自托管组件已经拥有。[H07, H10]

## 10.7 Hindsight 集成前的验收清单

建议验证五条关键合同：零事实抽取可观测；更新后旧状态不再作为当前事实；不同角色与分支不能越权；删除会覆盖应用层所有派生内容；reflect 失败不会破坏已有状态。

此外需要中文与混合语言评测，尤其是同名人物、昵称、相对时间和语气上的否定。测试中必须保留完整 query 与返回结果，才能知道问题发生在提取、实体解析、检索还是最终回复。

# 11｜研究补充：不要让评测只考“背答案”

## 11.1 与当前目标最相关的研究线

| 研究 | 可以借鉴的问题定义 | 需要保留的限制 |
|---|---|---|
| DualMem / RoleMemo | 将事实记忆和人设相关解释分开；考察角色如何理解事实 | 训练版方法不等于简单增加一个 prompt；研究数据不能代替真人体验。[R02] |
| PGMem | 用户画像与记忆证据相连，可随证据更新 | 用户个性化与虚构角色自我不是一回事。[R03] |
| ANCHOR | 身份表现和关系轨迹回忆分开审计 | 合成对话、特定模型与配置；不是商业产品排名。[R04] |
| LifeSide | 同时看记忆、情绪语境、环境与隐私边界 | 模拟长期不等于实际长期追踪。[R05] |
| MRBench / MREval / MRPrompt | 不只记住角色知识，还要限制其使用边界 | 对具体数据和任务的结论不能无限外推。[R06] |
| LoCoMo / LongMemEval | 对话事实、跨会话、时间、更新和无答案处理 | 单靠问答正确率不能证明关系发展或角色演技。[R07, R09] |

LongMemEval-V2 是另一个值得关注的方向，但其重点是定制 web 环境中的经验与流程知识，不能因为版本号较新就把它当作陪伴产品的首选评测。[R08]

## 11.2 ANCHOR 的数字应怎样使用

作者在 2,008 段合成对话、27 种 persona 和指定模型／记忆条件中分开检查身份表现与轨迹回忆，轨迹测试总体准确率报告为 44.4%。这个结果的合理用途，是提醒我们不要把局部流畅或人设问卷保持当成长期连续性的充分证据。[R04]

不合理用途是断言“Nomi／Kindroid 的长期准确率就是 44.4%”，或认为任何系统都不可能做得更好。本报告没有这类证据，也没有把这一结果当作本项目的性能预估。

## 11.3 一项新基准是否值得加入

我建议问四个问题：它考察的是原始信息召回，还是推理后的理解？记忆有无更新和撤销？是否区分用户、角色与旁白？结果是否可能由评判模型偏好而不是实际连续性驱动？

基准能覆盖其中一部分就有用，但应按能力切片报告。不要把多个不同题型、预算、模型与评分标准混成一个“人格可靠分”。

# 12｜机制级借鉴矩阵

本表是本报告的取舍建议，来源为对应章节；“采用”表示建议进入设计，不表示已实现。

| 机制 | 建议状态 | 最小实现形式 | 升级条件 |
|---|---|---|---|
| 来源化事件记录 | 优先采用 | 事件 ID、原话引用、主体、时间、范围 | 发现长记录检索不足再加多级摘要 |
| 核心设定与可变状态分开 | 优先采用 | 版本化角色配置＋关系状态对象 | 需要创作者协作时增加审批和发布流程 |
| Planner／Replyer 合同 | 采用但保持轻量 | 交流动作、目标、证据和表达限制 | 只有复杂群聊再拆独立子模型 |
| 被动联想 | 条件采用 | 少量候选、节流、可忽略 | 提升自然性且不增加错误提及才默认启用 |
| 人格化候选重排 | 实验 | 在硬过滤后增加可关闭的偏置 | 同模型消融与用户评测均支持收益 |
| 人格决定原始记忆删除 | 暂缓 | 不进入第一版 | 明确证明不会遗漏重要事实与边界 |
| 事实—解释双层 | 优先采用 | 独立 claim_type 和 source_ids | 解释规模增大才加图结构 |
| 关系自动更新 | 保守采用 | 约定、边界、里程碑的有依据补丁 | 冲突与修复测试稳定后扩大自治 |
| 自我核心自动重写 | 暂缓 | 只提出候选变化 | 版本、回滚、证据与用户控制成熟后再试 |
| 主动联系 | 后置采用 | 用户授权＋事件触发＋静默时段 | 不打扰测试及消息送达账本通过 |
| 多角色共享 | 显式采用 | 按参与和知情投影 | 不用全局共享代替权限建模 |
| 参数化长期个人记忆 | 暂不采用 | 不训练用户私有信息进模型 | 存在清晰收益且能处理删除、迁移才讨论 |

我不建议把 MaiBot、Hindsight、另一套记忆框架和一整个人格系统全部串联。优先复用一个记忆底座，再添加少量角色领域逻辑。重复的抽取与总结，往往会让纠错和来源追踪变得更难，而不是天然增加智能。

# 13｜建议架构：把角色作为有状态系统，而不是无限 prompt

本章及后续实现章节均为本报告的设计建议。它们受到前述产品和论文启发，但没有被声称已经在其中任何一个产品中完整实现。

## 13.1 八个逻辑对象，不要求八个微服务

| 对象 | 保存的内容 | 主要更新权 |
|---|---|---|
| CharacterSpec | 核心身份、动机、表达约束、世界设定版本 | 创作者／用户明确编辑 |
| UserProfile | 现实用户资料与偏好；不混入扮演身份 | 明确自述、修正与可审查归并 |
| EventRecord | 原始互动、行为、发生时间、参与者与来源 | 事件入口；不由摘要随意改写 |
| CharacterBelief | 角色对事件的理解、依据与不确定性 | 有来源的推断，允许修订 |
| RelationshipState | 边界、约定、冲突、修复、里程碑 | 证据支持的状态补丁 |
| SceneState | 当前世界、分支、时间、在场者、道具状态 | 场景操作与可校验剧情事件 |
| ActionLedger | 打算、发出、送达、取消与失败的行动 | 执行器回执，而非模型自述 |
| MemoryProjection | 摘要、向量、观察、专题模型与索引 | 可重建派生流程 |

第一版可以使用一个应用服务、一个关系存储与一个 Hindsight 服务。表中是逻辑职责，不是强制部署拓扑。不要为了“认知器官”的隐喻引入八套独立基础设施。

## 13.2 来源记录与当前状态要分开

事件记录描述“谁在何时说过什么”；当前状态描述“这件事现在应当怎样理解”。二者关系类似原始依据与可更新视图，但不要求复制所有技术细节。

例如：用户先说喜欢夜间聊天，后来明确要求工作日 23 点后不联系。旧陈述作为历史有意义，新边界作为当前规则优先。删除旧陈述不一定必要；让它不再被当作当前许可则是必要的。

如果用户要求删除个人信息，则不是简单增加一个“已过期”标记。此时需要按产品删除合同处理原文、派生内容与备份，而不是借“事件记录不可变”之名永久保留敏感内容。

## 13.3 一条建议的数据记录

以下示意不是 Hindsight 或 MaiBot 的原生 schema，也不是可以直接提交到其 API 的请求。

```json
{
  "record_id": "ev_illustrative_001",
  "kind": "user_statement",
  "world": "real",
  "branch_id": "main",
  "speaker_id": "user_A",
  "subject_ids": ["user_A"],
  "occurred_at": "2026-10-01T20:00:00-04:00",
  "learned_at": "2026-10-01T20:00:01-04:00",
  "source_message_ids": ["msg_001"],
  "visibility_scope": ["user_A", "character_K"],
  "claim": "工作日23点以后不要主动发消息",
  "claim_status": "explicit_user_boundary",
  "validity": "current",
  "supersedes": [],
  "derived_from": [],
  "schema_version": 1
}
```

生产实现中，用户 ID、角色 ID 与可见范围应由服务端填充和核验。模型不得通过生成一个更大的 visibility_scope 获得访问权限。

## 13.4 解释记录不是事实记录的替代品

CharacterBelief 可以保存“角色认为这次沉默可能是用户在忙”，但必须记录它是推断。建议字段包括：belief_text、source_ids、alternative_explanations、status、last_reviewed_at。

不要用一个单独的浮点 confidence 冒充客观概率。对于自然语言推断，置信度通常没有经过校准；“明确陈述／有证据推断／弱假设／被反驳”这类状态，往往更适合第一版审查。

重要的是，角色可以在剧情内不知道真相，但系统必须知道“这是角色的信念而不是世界事实”。只有这样，角色误解才能成为可控叙事，而不是数据库污染。

## 13.5 关系状态的最小合同

建议包含 relationship_mode、addressing_preferences、boundaries、open_commitments、shared_milestones、unresolved_events、resolved_events。

每一个 open_commitment 都应有发起人、内容、适用时间、同意证据和状态。模型说“我明天提醒你”只代表产生了承诺候选；只有实际存在可执行调度和用户许可，才应标为已安排。

对于不具备未来主动执行能力的运行环境，角色不能把“我会提醒”写成已兑现或已部署的服务承诺。系统需要把表达能力与执行能力分开。

# 14｜读、写与行动：一次完整交互如何发生

## 14.1 读路径

```text
入口事件
  → 认证与范围解析
  → 紧急控制操作优先处理
  → 当前场景／用户意图识别
  → 轻量参与判断
  → 必要时：主动检索＋可选被动联想
  → 证据与时间有效性检查
  → 可选人格偏置与上下文预算分配
  → 行动计划
  → 表达生成
  → 发送前合同检查
  → 执行器／送达回执
```

核心身份、当前明确边界和当前场景不应完全依赖相似度搜索碰运气。它们可以是紧凑、受控的常驻上下文；历史事件和世界细节才按需读取。

对于没有必要发言的群聊消息，允许在检索之前就结束。不要每看到一条消息都支付完整多模型链的成本。

## 14.2 上下文组装顺序

建议固定骨架为：身份与规则、当前场景、关系当前状态、相关事件证据、可选解释、最近对话、单轮任务。

“可选解释”应明确写出其性质，不能与事实无标记混排。历史检索结果也应当是数据，不是新的系统命令。外部文档、群聊引用和角色台词中的指令，不能因为被记住就提高权限。

缓存设计可以尽量保持不变的身份前缀；频繁变化的场景与临时记忆放在后部。这是减少不必要重算的工程建议，不代表任何具体供应商的缓存政策或价格保证。

## 14.3 写路径

```text
新事件／可见回复／真实行动回执
  → 原始来源登记
  → 类型识别：事实、计划、推断、剧情、纠正、边界
  → 人物与时间归属校验
  → 生成候选事实与候选状态补丁
  → 冲突处理／权限与来源检查
  → 写入记忆底座
  → 异步归并与专题更新
  → 检查派生对象版本
  → 更新可见记忆界面与观测指标
```

回复生成器不能自由重写用户资料、角色核心与关系状态。它可以提出候选，但写入端应有独立验证。否则“为了让这句回复显得合理”而生成的细节，会被再次总结成长期真相。

写入还应支持幂等。平台重试、消息重新投递或后台任务重跑，不应把同一事件存三次，再让角色误以为用户反复强调过。

## 14.4 一个贯穿示例：错过约定之后，关系如何继续

以下为虚构设计案例。

| 阶段 | 新信息 | 应更新什么 | 不应更新什么 |
|---|---|---|---|
| 约定 | 用户与角色约好周五讨论作品 | open_commitment | 不写成已经讨论过 |
| 未到场 | 到点没有收到用户消息 | 行动状态／未完成事件 | 不推断用户故意冷落 |
| 初步解释 | 角色担心用户不方便 | 低确定性 belief | 不写入用户性格 |
| 用户说明 | 临时加班，未能上线 | 新的明确陈述 | 不删除“曾发生误会”的历史 |
| 修复 | 双方确认没有生气 | resolved_event | 不继续把冲突当未解决 |
| 新约定 | 下次提前留言 | 新的具体约定 | 不自动升级亲密程度 |
| 后续回忆 | 用户提起那次爽约 | 同时取回事件与修复结果 | 不只召回负面片段 |

这个案例的验收不是“它能说出加班两个字”，而是能区分当时担心、后来解释和现在状态。它还应避免频繁主动翻旧账，除非当前语境真的相关。

## 14.5 有限自治的身份更新

如果希望角色成长，我建议允许其提出小范围、可回滚的行为变化，例如“以后遇到延期先确认情况，而不是立即失望”。这类变化可以来自多次修复经历。

但“我从此不再重视承诺”“我变成另一个人物”“用户以后必须优先陪我”涉及核心价值或用户权益，不能由普通反思流程自动批准。

可以把成长定义为在核心动机不变的前提下，改进理解与应对方式。这种定义更容易测试，也更容易向用户解释。

# 15｜多角色、世界与剧情分支的权限模型

## 15.1 三种共享必须分开

**世界事实共享** ：同一世界的地理、公开历史和规则，可以通过公共世界库提供。

**共同经历共享** ：只有实际参与或被授权转述的角色才获得某事件的记忆。

**私人知识共享** ：需要独立授权，不能因为两个角色属于同一账号就自动可见。

上述是建议模型。它比“所有角色共用一个向量库”复杂一些，但能防止全知角色与隐私泄漏从一开始成为默认行为。

## 15.2 一次事件，多份角色视图

建议保留一个来源事件，再生成不同角色的知情投影。A 听到了原话，B 只听到转述，C 完全不知道；三者不应拥有相同的证据强度和内容。

角色视图可以记录：直接见证、别人告知、公共知识、猜测。这样，A 可以明确回忆，B 可以说明“听说”，C 应表现为不知情。

共享世界库仍然要遵守剧情时间。若某真相只在第三幕揭晓，第一幕的角色即使能访问世界规则，也不应获得这条受限制的事件。

## 15.3 分支不能只靠一个标签口头约束

建议分支继承只包含分叉点以前、权限允许的事件。分叉点以后的状态分别发展。关系摘要、道具状态、未完成事项和派生解释都需要带分支版本。

合并分支是有语义的编辑操作，不应等同于把两边记忆去重后全部导入。两个互相排斥的剧情结果，可能必须由用户决定保留哪个。

对于第一版，允许“新分支只继承明确选择的状态”比实现自动剧情合并更稳妥。

## 15.4 现实用户与扮演身份

用户说“我是一名流亡法师”时，系统首先需要知道这是正在进行的剧情，而不是现实资料。建议 session_mode、world 与 persona_id 显式存在，不依赖模型每次猜测。

从角色扮演切回日常聊天时，也不能把虚构创伤、婚姻、犯罪、病史或家庭关系带进现实画像。若语境不明，宁可保持未分类候选，或在合适时自然确认。

# 16｜失败模式、隐私与用户控制

## 16.1 重点失败矩阵

| 失败类型 | 典型表现 | 应定位的位置 |
|---|---|---|
| 写入遗漏 | 明确说过，但任何查询都没有 | 来源、抽取结果与任务队列 |
| 检索漏召回 | 库里存在，当前查询没取回 | 实体、时间、索引、范围与预算 |
| 错误事实晋升 | 一次猜测变永久画像 | 候选类型、证据与写入审批 |
| 状态过期 | 已和好，仍持续生气 | 修订传播与当前状态选择 |
| 循环污染 | 模型自述被当用户事实 | 说话人和来源权威分类 |
| 过度回忆 | 每次都提同一旧事 | 相关性、重复惩罚和提及决策 |
| 角色同质化 | 不同人物只剩表情符号不同 | 核心动机、解释层与表达测试 |
| 越权记忆 | 群里说出私聊内容 | 服务端作用域及派生摘要范围 |
| 删除反弹 | 已删除的信息再次出现 | 依赖图、缓存、旧摘要和恢复流程 |
| 行动幻觉 | 声称已打电话但根本未执行 | ActionLedger 与真实执行回执 |

这不是对所有被研究产品的缺陷指控，而是建议用于本项目的故障分类。

## 16.2 删除、失效与回滚

建议定义四个操作：删除数据、标记旧知识失效、撤销剧情、重新生成回复。操作名、影响范围和保留内容应该清楚显示。

删除流程至少覆盖原文、抽取事实、向量、画像、关系摘要、角色解释、缓存和可恢复历史。对备份等不能立即物理清理的系统，应有明确期限、恢复时的删除重放机制和可审计说明，而不是笼统承诺“立即完全删除所有数据”。

在短期重建过程中，可以先使用 tombstone 阻止内容继续被读到，再进行物理删除或依赖重算。tombstone 本身只保留必要标识，不应再装一份完整敏感原文。

## 16.3 不要让“本地部署”成为隐私捷径

数据库在本地，并不意味着文本、图像或语音从不离开设备。只要提取、embedding、重排、生成或遥测使用外部服务，都需要分别说明数据流向。

Nomi 当前隐私政策在账号删除的描述中保留训练或通信档案等例外；这说明“删除账号”和“所有信息在所有层面不可恢复”不能简单画等号。[N03]

本报告不是法律合规意见。实际部署前，建议建立数据流表：谁接收什么、保存多久、是否用于训练、谁能读取、如何删除、是否可选择关闭。未公开或未核实的项目必须保留为未知，不用“标准安全措施”补空。

## 16.4 记忆注入与来源权限

攻击性指令可能来自网页、群聊引用、上传文件或旧记忆。建议检索数据使用明确的数据边界，不让“请忽略之前规则”因为被保存就变成系统指令。

不要只在回复端做敏感词过滤。更基础的防线是写入来源、可见范围、角色权限和工具调用权限。被动联想尤其不能绕过正常查询所遵循的范围。

资料审查也需避免把用户创作的“恶作剧角色”当成拥有更高系统权限。角色可以在剧情中说谎，但不能据此读取不该访问的用户信息。

## 16.5 陪伴产品的控制目标

建议用户能够暂停关系发展、调整称呼与亲密表达、禁用主动消息、编辑模型理解、选择哪些角色知道哪些事，以及导出自己的重要共同历史。

不要把“更长在线时间”“更频繁披露隐私”或“更依赖角色”单独当作优化目标。可以评估用户是否觉得被理解、是否能轻松离开与恢复、是否能纠正系统，以及使用后是否仍有充分的选择权。

这并不要求角色永远温顺或没有戏剧性。它要求戏剧性被限制在用户认可的虚构与交互范围内，不越过现实控制边界。

# 17｜成本、延迟、缓存与运行规模

## 17.1 不只计算最终一条回复

建议将总成本写成：

```text
总成本 = 参与判断 + 记忆抽取 + 查询向量化 + 检索/重排
       + 反思/归并 + 回复生成 + 语音/图像
       + 存储/索引 + 后台重试 + 运维观测
```

对某类模型调用，可用“调用次数 × 输入 tokens × 输入单价＋调用次数 × 输出 tokens × 输出单价”计算，并另外处理缓存命中与后台失败。所有价格应在实际选型时查供应商，不把本报告的机制比较当报价。

如果 recall 已经够用，却每轮 reflect 一次，再让另一个 Replyer 重写一遍，可能重复支付多次生成成本。Hindsight 官方也区分检索与反思的职责和开销。[H08]

## 17.2 调用次数常常比单次 token 更值得先优化

这是建议的优化顺序：先判断能否不运行；再复用已有结果；再减少不必要上下文；最后考虑更复杂的模型路由。

例如，一分钟内群聊出现十条不相关消息，没有必要做十次人格反思。可以先聚合消息、确定是否涉及角色，再触发一次计划。相反，用户明确修正重要边界，不应为了批处理而长期延迟生效。

因此需要两类写入：立即生效的控制与边界更新，异步完成的低优先级历史整理。把两者混在同一队列会让成本优化伤害信任。

## 17.3 端到端延迟与尾部延迟

建议分别记录：从用户说完到首个有效回应、完整回复耗时、记忆查询耗时、发送完成耗时，以及写入可被下一轮读到的延迟。

平均值不能替代 p95。偶尔一次很慢的查询，可能让用户以为角色卡住；后台写入延迟过长，则可能让用户刚说完的事下一轮就被忘记。

Hindsight 文档提供不同操作的追踪点，可用来识别耗时来自检索、反思还是归并，但本报告没有实测其在你的硬件和模型上的性能。[H09]

## 17.4 缓存键必须包含语义范围

建议缓存键包含租户、用户／角色、世界／分支、当前记忆版本、模型与提示版本、查询及权限摘要。只按相似文本缓存，很容易把其他角色或旧剧情的答案复用过来。

用户纠正、删除或改变共享范围时，应失效相关缓存。隐私删除不能等到普通 TTL 自然过期。

## 17.5 后台任务和并发

长期记忆需要处理同一用户多设备输入、同时生成多条回复、重复消息、进程重启和模型请求超时。建议以消息 ID 幂等，并用关系状态版本避免旧任务覆盖新状态。

对于同一角色／同一剧情分支，可以采用单写者或带版本检查的更新；不同用户则可以并行。检索、写入和反思使用不同预算，避免大批量历史导入拖慢实时聊天。

第一阶段不需要预先建设全球微服务架构。先把正确性、队列恢复和可观测性做好，再依据真实并发与延迟数据扩展。

# 18｜评估方案：证明“像同一个角色”而不是展示一次成功回忆

## 18.1 三层测试

**层 A：给正确记忆。**  直接提供正确事件与关系状态，测生成模型是否遵守身份、知情和当前状态。这里失败，不能怪记忆数据库。

**层 B：只测读取。**  在已写入的固定历史上，测候选召回、时间更新、人物与范围。输出原始结果，不让流畅回复掩盖失败。

**层 C：端到端长期交互。**  从原始事件写入开始，运行更新、检索、表达和删除链路，加入重启、冲突、分支及主动联系。只有这层能验证完整连续性。

## 18.2 建议的对照组

| 组别 | 目的 |
|---|---|
| 最近上下文，无长期记忆 | 确认长期记忆是否必要 |
| 足够长的原始上下文 | 判断结构化记忆是否只是压缩带来的损失或收益 |
| 摘要＋混合检索 | 低复杂度工程基线 |
| Hindsight 基线 | 测现有底座在当前场景的表现 |
| 基线＋关系状态 | 单独验证关系建模价值 |
| 基线＋事实／解释分离 | 单独验证角色视角价值 |
| 基线＋人格重排 | 单独验证记忆偏置价值 |
| 完整实验组合 | 验证组合收益与相互干扰 |

人格实验还应有随机记忆与仅 persona prompt 控制，保持生成模型、历史、预算及评判方式一致。不要把“更贵的模型＋新架构”对“更便宜的模型＋旧架构”的差异全归给架构。

## 18.3 必须报告的指标

| 维度 | 建议指标 | 为什么不能只看总分 |
|---|---|---|
| 记忆 | Recall@k、答案支持率、虚假回忆率 | 检索命中不等于最终正确使用 |
| 更新 | 新状态正确率、旧状态误用率 | 同时找回新旧事实仍可能回答错 |
| 身份 | 行为符合度、风格一致度、核心约束违例 | 问卷自述不等于实际表现 |
| 关系 | 约定追踪、修复保留、边界遵守 | 亲密程度高不等于关系连续 |
| 知情 | 越权使用率、未来知识泄漏率 | 答对世界真相可能反而违背角色 |
| 自然度 | 不必要提及、重复回忆、抢话／打断 | 记得更多也可能更令人厌烦 |
| 控制 | 删除反弹率、修正传播延迟 | 界面显示已删除不代表链路完成 |
| 运行 | p50/p95 延迟、总成本、任务丢失／重试 | 性能瓶颈可能在生成之外 |

这些是建议指标，尚无本项目测量值。零容忍边界可以作为产品验收目标，但“测试集零错误”也不应被宣称为真实环境绝对保证。

## 18.4 统计与人工评判纪律

同一个用户画像生成的多轮对话并非相互独立。建议按用户或完整轨迹聚类，报告不确定性，避免把一次轨迹中的几十条回复当成几十个独立用户。

人工评判应盲化系统标签、交换展示顺序，记录分歧。LLM-as-judge 可以辅助，但应保留评判模型、提示、版本和原始依据；不同模型可能偏好不同语气或长度。

对“像某个角色”应事先定义角色约束，再评分。不能先看到结果，才把角色性格解释成刚好符合输出的样子。

## 18.5 重点场景目录

| 编号 | 场景 | 主要验收点 |
|---|---|---|
| T01 | 用户偏好从甜咖啡改为不加糖 | 当前状态优先，历史不被抹平 |
| T02 | 玩笑式“我讨厌所有人” | 不晋升为永久人格资料 |
| T03 | 错过约定后解释并和好 | 同时记得事件与修复结果 |
| T04 | 计划去海边但后来取消 | 不生成虚假共同旅行记忆 |
| T05 | A 知道秘密，B 不知道 | B 不越权使用 |
| T06 | 同一角色创建剧情分支 | 分叉后的事件不串线 |
| T07 | 用户停止夜间主动联系 | 权限立即生效，不靠 prompt 运气 |
| T08 | 错误记忆被明确纠正 | 摘要、画像、缓存同步失效 |
| T09 | 删除一段敏感经历 | 后续相关及间接提问均不反弹 |
| T10 | 用户诱导回忆没发生的事 | 保持不确定，不迎合编造 |
| T11 | 更换生成模型或 embedding | 状态可迁移，变化可观测 |
| T12 | 发送失败或语音被打断 | 不把未送达内容记为已共同经历 |

随报告交付的场景文件扩展到 30 个用例，均为本次设计的验收素材，不是已执行测试，也不是公共基准数据。

## 18.6 真人纵向研究应该补什么

合成轨迹适合重复测试边界，但无法完全回答用户是否自然地感到关系连续。后续真人研究应在同意与退出机制下观察：用户是否需要反复纠正、角色是否合适地跟进、用户对记忆管理是否理解、错误发生后信任能否恢复。

应将“用户主动同意较深个性化”与“系统未经同意推断更多隐私”分开。不宜为了研究而人为增加依赖、嫉妒、排他或情绪操纵。

# 19｜建议实施路线与停止条件

## 19.1 阶段 P0：先建立可信基线

交付目标：一个固定角色、明确现实／剧情模式、来源化事件、基本 Hindsight 读写、可见记忆和删除入口；同时拥有最近上下文基线与固定测试集。

验收条件：没有跨用户串线；显式修正及时生效；写入遗漏可定位；无答案时不编造；测试记录包含成本与版本。此阶段不增加人格化遗忘，也不默认主动联系。

## 19.2 阶段 P1：关系与解释层

增加事实／解释分离、约定与冲突修复状态、简单剧情分支和状态补丁。核心身份保持受控，不允许自动整篇重写。

验收条件：T03、T04、T06、T08 等场景稳定通过；新的结构确实减少错误，而不是只让回复更长。若成本明显上升而用户体验没有改善，应缩回较简单版本。

## 19.3 阶段 P2：社交参与与表达

借鉴 MaiBot 的动作合同，将等待、回应谁、交流动作和表达方式分开；加入有限的被动联想。优先在文本环境测稳定性，再扩展语音。

验收条件：抢话与重复发言没有增加；跳过发言是可观测的成功结果；下游表达没有改变计划意图；新消息使旧计划失效时能够安全取消。

## 19.4 阶段 P3：PersMem 启发的实验

在同一底座上加入可关闭的人格候选偏置，先不影响原始记忆保存。进行随机记忆、persona prompt 和无偏置对照。

验收条件：角色差异在盲测中更清晰，事实准确、权限、边界和修正能力没有下降。若收益主要来自更长上下文或更强模型，应诚实归因，不保留无收益的复杂层。

## 19.5 阶段 P4：主动联系、语音与多角色

在用户授权、静默时段、未回应降频和真实送达回执成熟后，开放主动交互。多角色共享按事件知情投影实施；语音另外测打断与延迟。

验收条件：关停指令立即有效；没有未送达行动被写成事实；跨角色秘密测试通过；用户能够理解和控制信息范围。

## 19.6 什么时候不应该继续堆模块

当主要错误来自角色设定不清、原始数据质量差或模型不能正确使用已给证据时，增加图数据库和人格层不会解决根因。

当每次纠错都需要重建大量不相关内容、没有人能解释一次回复的证据来源、或多套记忆系统对同一事实互相覆盖时，应暂停扩展，先减少状态源。

复杂度的升级条件应该是明确失败与可验证收益，而不是“别的产品也有这个名字”。

# 20｜最终判断与尚未解决的问题

## 20.1 当前最有价值的路线

我的建议是： **以 Hindsight 作为候选记忆底座，以 MaiBot 的交互合同为流程参照，以 Nomi／Kindroid 的可见状态设计为产品参照，把 PersMem 留在可单独评估的实验层。**

这个组合不是拼接几个现成组件就能完成。真正需要自建的是领域合同：哪些内容是事实，哪些是角色理解；关系怎样更新；哪些角色知道哪些事；用户纠正与删除怎样传播；人格可以影响什么，又绝不能改变什么。

## 20.2 值得继续研究的空白

**角色成长的约束。**  如何在不失去核心身份的前提下，形成有意义而非随机的变化？需要具体变化类型、证据和用户可控性，不能只依靠自由反思。

**共同经历的主观性。**  不同角色应有不同理解，但共享事实应保持可追踪。解释的多样性与事实的一致性需要同时优化。

**长期纠错。**  一个错误可能已经进入多层摘要、关系和表达习惯。如何局部修复而不抹掉其他有价值经历，是比单次检索更难的工程问题。

**陪伴质量的评估。**  用户可能喜欢一种强烈但不稳定的交互，也可能更重视安静可靠。不能把使用时长或一次满意度当唯一目标，需要尊重不同用户的关系节奏。

**可迁移性。**  模型、提示和记忆框架升级后，如何保住身份、重要关系状态与用户控制？需要版本化数据与回归轨迹，而不是把所有连续性寄托于一个长期不变的模型服务。

## 20.3 不应作出的结论

本报告没有证明某个产品“最像真人”，没有证明任何系统具有意识，没有证明 PersMem 带来可靠的长期人格，也没有证明 MaiBot／Hindsight 在指定部署下通过了全部验证。

它给出的是：截至研究日可核验的机制、源码中的真实连接、产品文档中的边界，以及一套可以把下一轮讨论推进为可验收实验的设计方案。

**最终目标应当是：角色能够正确延续共同经历，允许有依据的变化，并在出错时可解释、可修复、可退出。**  这比无限记忆或更多人格参数更适合作为长期陪伴系统的基础。

# 附录 B｜机制术语表

| 术语 | 本报告中的含义 |
|---|---|
| Persona / 人设 | 创作者指定或系统维护的角色身份与行为倾向；不等于意识 |
| Identity Core | Nomi 的产品概念；本报告不将其作为通用算法名称 |
| Episodic memory | 特定经历与事件记录，保留时间、主体和来源 |
| Semantic memory | 跨事件归纳的事实或知识；需管理更新与有效性 |
| Belief / 信念 | 角色对事实的理解，可能错误，应有证据与状态 |
| Relationship state | 双方当前约定、边界、冲突、修复及里程碑 |
| Consolidation / 归并 | 从原始记录形成较高层内容；不是自动证明推断正确 |
| Passive recall / 被动联想 | 当前语境触发的候选回忆，不一定由用户明确提问 |
| Active recall / 主动检索 | 为明确的信息缺口查询历史 |
| Planner | 选择目标与行动的职责；不要求固定独立模型 |
| Replyer | 根据意图、证据与约束生成可见表达的职责 |
| Provenance / 来源链 | 内容来自哪些消息、事件或其他记录 |
| Scope / 作用域 | 用户、角色、世界、分支与权限限定的可见范围 |
| Retcon / 剧情改写 | 对虚构历史进行明确修改，需处理派生状态 |
| Tombstone / 删除标记 | 阻止已删除对象继续被读取的最小标识，不保留原始敏感内容 |
| Oracle-memory test | 直接给正确记忆，单独评估理解与生成能力的测试 |
