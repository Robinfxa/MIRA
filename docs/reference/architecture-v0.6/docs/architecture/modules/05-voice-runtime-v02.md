# M05 语音 v0.2 基线与多模态增量

> **v0.6整合说明：** 原架构合同继续有效；本章新增“复用落点”只将借鉴书的既有证据和建议接到本章。具体技术栈未由本次整合自动批准；差分见A4，源码原阅读范围见A5。


**地位：** 用户指定v0.2为基础。本章忠实整理其运行机制；供应商、数值与实验开关保留来源地位，不冒充本产品新验证结果。  
**依据：** V02 §1–19、§21–22；H1 §1、§4；H2 §7、§11；PEER §1–8；D5；G3R §6、§9–10。 D6；G4R（相关小节见正文）；ADR-0006。

## 1. 五个逻辑面和一个会话权威

Character Plane定义角色逻辑；Intelligence Plane负责主生成；Semantic Control Plane提供Input／Output判断；Performance Plane负责TTS与预制音频；Realtime Runtime独占版本、截止时间、取消、缓冲、授权和观测。[V02 §1]

主路线名称保留为Streaming ASR＋JEV＋Luna＋Streaming TTS＋可取消运行时；名字表示来源中的候选职责，不保证具体模型、账号或服务已可用。MVP不新增常驻表达规划服务、语义同步服务或重量级工作流设施。

所有角色人声进入同一个Playout Arbiter。多模态扩展可以协调视频／动作中的人声，但不能另建播放器绕过话轮、停止和当前约束。G04允许预审雨声等无新语义维持在普通“停止回应”后保持；明确全部静音覆盖正文、等待语、视频人声与环境音。具体混音参数仍需验证。[D6；G4R §3–4]

## 2. 输入先累计，判断读完整快照

客户端采集保留真实采样率、通道、sample位置与单调时间。回声和本地活动处理在角色说话时继续；不能把错误采样率标记当正确数据，也不能只关闭麦克风来避免打断。[V02 §5.1]

规范化输入区分：转写是否稳定、语义是否完整、用户是否让出话轮。原始ASR delta先应用修订、去重与累计，再生成自足快照。一个in-flight＋一个latest pending只适用于完整输入判断快照，不适用于原始delta、停止事件或回执。[V02 §5.2–5.4]

中文“不、没、但是、我还没说完”等首音与修订是重点。同行研究提议短时pre-roll与真实收音链路回归，而非仅测预裁切WAV；具体缓冲与隐私保留策略尚待实现验证。[PEER §7]

## 3. 推测：可以提前算，不能提前相信

v0.2区分S0只读预取、S1文本推测、S2音频准备。当前候选依赖原始输入revision、已验证revision、角色与上下文版本、output_epoch和预算。新输入先撤销播放资格；兼容可重新验证，不兼容则废弃相关未播内容。[V02 §6]

来源MVP设单会话最多一个推测generation、只预合成首段；这是来源实验范围，不意味着本书批准多候选树。每轮重启、token、音频与保留时间均有界；推测不进行不可逆外部操作，不写共同经历。

首段审查与TTS并行是另一个默认关闭的实验，不等同于说话结束前推测。它要求外传／合成授权、精确冻结内容与参数、服务端隔离队列和有界预算。审批前不得向客户端发送隔离音频，同流不混入第二段未批准正文。拒绝、修改、失效或超时使旧隔离结果废弃。[V02 §6.5、§9.4]

## 4. 输出队列与语义边界

```text
LLM token ≠ 语义片段 ≠ TTS输入单元 ≠ 音频packet
```

原始文本delta有序累计；同一候选冻结前可修改；冻结后以精确版本进入有界FIFO。审核结果可以乱序到达，但发布只推进连续已批准前缀。不能让后来的C覆盖必要的B，也不能跳过被拒绝的限定条件继续后段。[V02 §8]

Chunker保留否定、转折、条件、人名、日期、数量单位与必要限定。时间或字数门槛只是候选边界触发，不构成强行切字的理由。

G03已经确认按完整语义充分范围增量审核／发布，一个范围可以跨多个beat。多模态不重写正文保序规则，不因范围合并丢掉必要限定；一个beat或审核范围不要求新建一次TTS，也不能以视觉最新状态覆盖文字FIFO。A整轮保守模式复用这些合同。[D5；G3R §5–6]

## 5. 表达策略与TTS能力

ExpressionPolicy在作用域内复用，分别约束措辞、TTS参数意图与filler选择；偏好不授予内容或执行权。软风格结果迟到不重启正确正文，实质语境改变则走输入有效性检查。[V02 §7.5]

每个provider／model／voice／locale／region组合应有能力记录：输入输出流、控制范围、取消范围、输入间hold、finish_input前是否产音、对齐及sample格式。未知能力不按支持处理；应用的情绪标签不等于厂商原生参数。[V02 §9.1]

默认尽可能连续推送已批准文本：`open → push* → finish_input → drain → close`。需要改全局配置时在适当边界重开，不能默认每个小片段并行一个TTS worker。

### 5.1 G03带来的跨模态依赖准入

内容获准不代表所有已批准台词都适合立刻送入同一条可播放TTS流。若“你看照片左边”依赖P1当前可见，而P1尚未显示，在缺少可靠文字—音频范围映射时，提前将它与前段混入同一流，就不能靠packet编号或字符比例阻止它提前出声。[G3R §10.1]

保守路径是在前置呈现条件成立前，不把这段台词推入无法可靠隔离的可播放流；另一种实现只有在能力已证明时，才可使用独立且可绑定、可隔离的流／音频范围。后者要记录额外开流、韵律、等待和预算成本，不能凭G03获批默认启用。[G3R §10]

依赖曾成立也不保证播放时仍成立：图片被替换、新输入或分支失效时，本地执行检查仍生效；无法精确局部切除则按§6取消旧流与未播尾部。具体准入／隔离方案、保持输入开放的能力与回退触发需适配验证。

审核范围较大不意味着一次性push全部文本。送入范围须已批准、连续，且不绕过呈现依赖；合规的无语音候选不创建空TTS，动作／控制字段不朗读。同一次主生成也不等于每beat一个TTS worker。

## 6. 对齐、领先量与缓冲

强制保留stream和sample层的消费与取消位置；逐字对齐若未知，不用字数比例或网络包号伪造。无法局部取消时，相关已送TTS内容失效就取消整条旧流与未播尾部，再依据已确认前缀和不确定末段续接。[V02 §9.3]

分别记录文本生成、音频合成和客户端实际／估计输出位置。TTS高低水位限制新输入，文本和音频总缓冲均有硬上限。停止读取网络不代表供应商停止计算；暂停期间在途音频仍可能继续到达。[V02 §9.5、§12.3]

服务端隔离／暂停暂存、客户端ready／jitter buffer、设备已提交输出是三类缓冲。前两类可受控丢弃未播范围；设备尾部要实测，不能宣称都可瞬时清空。

### 6.1 G04：暂停、停止与混合恢复

暂停时停止新增TTS push并有界暂存；远端和在途结果仍可能到达。永久失效立即取消旧工作、清理其可播尾部，迟到成功不得展示或发声；不为复用率继续保存无效分支。[G4R §10]

可靠sample游标不等于逐字对齐；纯PCM可否恢复按V02真实游标与完整条件判断，不能以无逐字时间一概否定。混合表演还要检查动作／视频／展示对象及语义依赖；声音可续不代表全表演可续，过期定时器不得追赶补演。[G4R §8]

语义恢复仍默认关闭，G04批准不启用该实验。停止后的新请求以因果关系重新开启新分支，不自动清除持续静默或全部静音；仅STOP不能触发filler或额外“好的”。

## 7. 等待语是有依据的行为，不是答案

Backchannel、Thinking Filler和Operational Preamble有不同speech-act许可；MVP重叠backchannel默认关闭。认同词不是通用加载音，“我查一下”需要真实查询依据。[V02 §10.1–10.4]

等待语绑定当前真实未完成任务、逻辑话轮、输入有效性、角色声音版本与一次消费。倒计时只提供检查时点，不创造发言理由。正文准备好优先正文；用户打断立即取消filler尾部，不能按正文方式续播半句filler。[V02 §10.5–10.7]

G01／G01.1带来的增量提案是：第一段实质非语音回应已开始后，不能因“第一段声音未出现”而继续首答filler；静默约束也应约束等待语和失败TTS。安静陪伴建立完成后，不能把已终结工作当持续发言依据。[H2 §7.1]

## 8. 账本与指标

Generated、Synthesized、Delivered三种记录分开；多模态扩展同源记录字幕、动作和媒体。下一轮不能带回未播放的完整旧回复。真实输出过的filler记为dialogue act，未消费许可不记为已说。[V02 §13]

来源的语音延迟定义为 `L_answer = max(t_ready, t_gate) - t_end + D_sink`，另计反馈延迟，不把filler或首token冒充实质回答。v0.2的挑战目标是普通无工具短回合p50≤500ms、p95≤1200ms，本地插话到静音p95≤150ms；这些是来源实验目标，未证明多模态系统达成，也非本次重新承诺。[V02 §14]

H2建议另外记录首实质交流效果、无语音建立完成时间和无意静默等，不用眨眼替代语音首答指标，不用动作“动得早”证明回应覆盖。[H2 §11]

### 8.1 G03的延迟收益边界

G03允许独立前段的审核／合成／呈现与后续生成重叠，可能减少等待剩余计划生成的时间；不保证降低模型首token、整轮时间、总token或成本。短回复可能几乎没有收益，审核排队与TTS衔接也可能抵消收益；媒体前置依赖可能才是瓶颈。[G3R §9]

A／B应按相同合同及可比较的模型、TTS、设备／网络条件分组测量；分别记录首实质交流行为、首实质语音、必需媒体可见和完整请求满足。不能用点头或filler掩盖答案变慢，失败样本与取消浪费不得从报告中消失。此处是验收设计，未提供新的实测数值。

## 9. 故障、增量与未决

输入、生成和缓冲失效时，保留已交付前缀并显式标明原因；不能截断中间正文后继续，也不能把异常终止伪装成正常完成。能力不足时牺牲复用优化，不牺牲停止、新鲜度与会话隔离。[V02 §8.5、§12.5、§16]

本章不决定新供应商、不核定账号权限、不强行改变既有声音路线。G03已选同一次主要生成、完整语义充分范围增量审核／发布；准确framing、范围映射和TTS依赖准入仍需冻结。G05已确认判断分工，实际后端准入归M02／M09，G02=A的wire适配仍需冻结；G04停止／保持／因果重新开始政策已确认，具体事件、作用域和适配实现归M04。首段并行、语义恢复、自适应领先量等仍按原独立实验门槛处理。

## 11. Codex订阅优先的主生成适配

D7将LLM承载优先级改为使用已有Codex／ChatGPT订阅额度并预留API，逻辑生成职责不变。保留Luna一词作为原资料候选来源，不保证当前账号仍能选择同一型号。实际模型、认证、版本和能力分别记录；中文角色性、语义首段与取消须重新验证。[M09]

订阅Responses薄请求或Codex app-server是不同适配候选，不能只换base_url即宣称等价。编码进度、计划、工具输出不进入TTS；只有受控范围的utterance进入原连续流。没有可靠结构化增量时采用G03-A，性能记录按实际模式分开。

原ASR与TTS接口、真实voice／locale、对齐、等待语和G04停止不因登录Codex而被替代。对话和图片共享计划额度时，图片任务需限流，不以“额度免费”增加无界推测合成或恢复。未授权额外API花费时不会自动切换收费路线。

## 12. 复用落点：语音基础设施与调度模式

### 12.1 Pipecat：现成流水线、服务适配和输出基础

固定提交`cae1f51a4060b6acf679991e75374520069ef016`。`BaseOutputTransport`已经处理音视频sender、分块、采样率、过滤器生命周期、正常停止与取消；`InterruptionFrame`是现有控制消息。无需从零建设一套音频传输与输出任务体系。[OS-C12](https://github.com/pipecat-ai/pipecat/blob/cae1f51a4060b6acf679991e75374520069ef016/src/pipecat/transports/base_output.py) · [OS-C13](https://github.com/pipecat-ai/pipecat/blob/cae1f51a4060b6acf679991e75374520069ef016/src/pipecat/frames/frames.py)

**首接入建议：**以Pipecat的一条传输／服务链承接STT/TTS与媒体传输，把MIRA许可检查放在明确的合成准入和实际输出接缝。用外部语义控制触发它的执行，不让框架默认话轮检测再次自动触发另一段LLM回复。

**借现成的：**连接与服务adapter、重采样接口、输出分块、取消清理、控制frame、已有服务示例。**自己补的：**Input完整快照、JEV结果归属、G03范围批准、G02快照安装、客户端本地stop latch和多模态回执。

本轮不在没有指定语音Provider和声线条件下宣称某个adapter已经满足中文音色、逐字对齐或设备尾部要求。需要的是对所选adapter做边界联调，而不是重新训练VAD、STT或TTS。

### 12.2 LiveKit：可选的RTC／Agent基础和SpeechHandle参考

固定提交`8de48c229655d10ca3df3274ba77c20eef50c6c1`。`SpeechHandle`已有scheduled、authorize、done与interruption的独立结构，还有任务、回调与失败读取。这是我们可以直接参考的生命周期实现，不应再将“区分已生成和已播完”描述成全新技术。[OS-C14](https://github.com/livekit/agents/blob/8de48c229655d10ca3df3274ba77c20eef50c6c1/livekit-agents/livekit/agents/voice/speech_handle.py)

对于需要RTC房间、浏览器传输和Agent集成的实现，LiveKit是Pipecat路线之外的候选。**不能把二者的默认会话主控、自动回复与音频播放都启动。**可以经正式适配组合传输，但必须只保留一个主生成触发者、一个角色人声仲裁和MIRA单写者。

源码中的`_authorize_event`等私有字段可用于理解机制，不直接当作稳定公共API依赖。实际接入应使用公开session／speech控制面，或提交最小、可回归的适配补丁。等待handle结束还应检查失败结果，不能把Future完成自动当成功。

### 12.3 浏览器VAD：已有库，不必造分类器

`ricky0123/vad`提供浏览器MicVAD、语音开始／结束回调，底层使用Silero与ONNX Runtime。借鉴书原核查读取项目资料，未深审源码或测量设备。[OS-W19](https://github.com/ricky0123/vad)

它应将活动通知送到R0，让本地先停，而不是直接声明用户已完成逻辑话轮。保留按住说话交互；额外声学检测不能吞掉首音节、丢掉“不”，也不能与另一VAD各自给Actor制造重复新话轮。预录缓存、采样位置、回声与移动端资源限制需要针对选定链路验证。

没有自动VAD也可以满足题目明确打断的基线；有库可用不等于必须同时开放所有自然附和／恢复实验。B2，第2–3页

### 12.4 AIRI：最值得借的是顺序和取消，不是默认并发数

固定提交`731123861093abfd7fc34c0654ba9f99206ab944`中的`packages/pipelines-audio/src/speech-pipeline.ts`已经有intent/owner级停止、AbortSignal、合成结果按sequence收集、播放start/end/interrupt/reject回调。[OS-C17](https://github.com/moeru-ai/airi/blob/731123861093abfd7fc34c0654ba9f99206ab944/packages/pipelines-audio/src/speech-pipeline.ts)

它对MIRA有直接启发：把**文本产生、TTS计算完成、实际播放完成**拆开；迟到完成必须先检查intent是否已取消；回调解除等待而不永久挂住下一项。可以适配这类接口，不必再设计一套万能音频任务框架。

但源码中的多个TTS任务并发，以及null结果后继续推进sequence，不能不加分辨地搬进MIRA。我们的普通声音优先连续TTS；必要限定对应片段失败时，不能跳过它继续播后文。可以保留队列算法，改变准入和失败收口政策，而不是把整套AIRI语音配置当默认真理。

### 12.5 Open-LLM-VTuber：中断历史已有可读实现

固定提交`992309c0aa19845960228f880013d4685fde93b5`的`handle_individual_interrupt`取消会话任务，再把`heard_response`交给Agent并保存中断历史。[OS-C18](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber/blob/992309c0aa19845960228f880013d4685fde93b5/src/open_llm_vtuber/conversations/conversation_handler.py)

这个模式非常接近MIRA的需求。应复用“打断回传已听前缀、停止旧计算、下轮用截取历史”的工作流；MIRA再补客户端身份、截止游标、partial/unknown、字幕与图片的独立曝光记录。不能仅因为客户端传了一个字符串，就声称精确证明用户听到了每个字。
