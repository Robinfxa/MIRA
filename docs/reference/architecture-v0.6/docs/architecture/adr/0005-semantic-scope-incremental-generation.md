# ADR-0005 G03：同一次主要生成，按语义充分范围增量审核和发布

**状态：已确认；架构路线生效，字段／算法／能力与性能仍待冻结或验证。**  
**来源：D5，发生于架构书v0.2及G03论证之后；不虚构逐条消息时间。**

## 1. 用户确认原文

> 同意，G03 采用同一次主要生成，以完整且具备充分语义上下文的范围增量审核和发布。一个范围可以包含多个 beat；必要后文未知时等待，必要时扩大到整轮。保留 A 作为同合同的保守模式和评测对照，不把 C 放入默认主链。

D5的准确范围是本ADR的批准依据。原论证G3R保留“待裁定”的历史字节；本ADR和模块回填才是当前决定，不改写旧稿来伪造当时已获批准。

## 2. 决定

同一次主要生成产出TurnPlan／PresentationBeat候选，以**完整且具备充分语义上下文的范围**增量审核和发布。一个范围可含多个beat；必要后文未知时等待，必要时扩大至整轮。这不是逐token、逐JSON片段或每beat到达即执行。

A保留为**同合同的保守模式与评测对照**，不另建一套执行器或绕过审核的fallback。C不进入默认主链；不据此声称额外导演调用在所有未来场景都没有价值。

## 3. 对既有决定的承接

G01允许无语音独立回应，G01.1保留前置约束／受限选择／完整审核，G02-A继续由Actor统一发放当前许可。G03决定内容何时构成可审、可发布的完整范围，不替代执行资格和真实回执。[M02–M05]

必要条件不得留到已发布内容的未知后文才补齐；时间／字数阈值不产生语义批准。已接受内容不可被后段原地改写，有界FIFO与连续已批准前缀保留。具体范围身份、冻结和局部失败规则在M03正文细化，语义解释仍可能有误，不宣称形式化无错。

## 5. 不隐含批准的事项

精确wire／framing、JSON或其它承载格式、消息名称、范围ID与摘要算法、必要后文判定阈值、合并策略、封口格式、模式配置、重试预算和生产启用参数仍需实现细稿。真实后端能否提供可靠结构化增量、TTS是否支持精确隔离、B是否更快／更便宜，均没有本次实测证明。
