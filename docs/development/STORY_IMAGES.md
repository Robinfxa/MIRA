# Bounded story illustrations: offline first slice

An explicitly injected per-session StoryImageRuntime connects an image backend, a PNG canonical decoder, independent pixel review, and a finite admission budget. No default app or CLI selects an image backend. Image/vision configuration strings alone do nothing. Real API activation still requires the separately approved exact routes/models, released-fiction data scope and spending ceiling. Subscription text is never redirected to paid images. No live image calls or credentials were used to validate this slice.

The initial capability is deliberately finite: the already public fictional lighthouse/coast picture, an empty cafe rain window, or an empty cafe table still life. Framing is wide/detail and lighting is scene_default/warm. Server-authored prompts exclude people, identities, writing, documents, real user memories, arbitrary briefs, unreleased plot facts and shared-trip claims. The existing fixed trip_photo remains an authored illustration. Every accepted new intent calls the injected generator; no resource cache grants permission.

Ordinary text can seal independently. The separately owned image task must have a reviewed intent, a reserved byte/cost/count budget, fully decoded canonical PNG and exact request/spec/content/policy-bound passes for every pixel check. Only then can its current reservation gain a single post-seal media effect. New input, Stop, Close, photo dismissal or timeout cancels/revokes outstanding work; ignoring task cancellation cannot restore authority. The qualified resource endpoint requires the session token and exact current effect/epoch/activity/resource/digest. Pixels are in memory only, bounded to four attempts/resources and 32 MiB per session. Cancellation and unknown outcomes do not refund attempt/cost reservations.

The browser must hash/decode these exact bytes, recheck the current grant, commit through the existing controller, and submit the exact receipt. Pending, failed and qualified-but-unpresented images are distinct from presented pictures. Next-turn generation and optional review receive a small shared generated_visualization projection, including the fallible pixel observation and actual receipt identity when present. It never writes user memory or promotes author canon, story history, or a real shared trip. No extra language-model call narrates the result.

Real visual quality, provider pricing/eligibility, authorized production factories and user-device display remain separate acceptance tasks. Fixture tests prove software boundaries only.


## Lifecycle review hardening

A valid proposal enters pending before optional JEV, with one application-owned request UUID retained through dispatch. Review identity is claimed once per accepted input/epoch/spec before any review await; repeat candidates cannot incur repeated image-intent reviews or relabel a running image. A later accepted input gets a fresh scope. Every hold/error path ends its pending status, and late old-review exceptions cannot mutate newer work. Dismissal immediately updates stored visibility facts.

Presented-effect history remains issuance-ordered for legacy fixed-only sessions. If generated photos participate, only the photo entries are normalized by exact receipt sequence inside their existing positions. Caption, speech, pose and scene positions, exact effect identities and cue associations remain unchanged. Snapshot construction consumes the same projection and retains strict validation. Persistence still pairs issued effects and receipts by effect ID; presentation order never reassigns receipts.

For explicitly configured providers, the runtime accepts an optional ImageOperationAdmission with synchronous reserve(request) and release(request_id). It reserves before the first provider await and releases active ownership only after the actual generation/decode/review coroutine settles, including cancellation-ignoring operations. A failed reserve reaches no provider. The gate's process-wide counters can survive session replacement; release is not a refund. Default construction has no gate and remains unavailable without the existing explicit factory and approvals.
