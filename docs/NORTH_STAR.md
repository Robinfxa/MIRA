## 新增硬约束：问题必须可定位

来源：2026-10-03 用户明确要求准备项目日志、报错并加入北极星；随后明确要求
加入会记录原始内容的开发模式。这是用户追加要求，不冒充原题 PDF 的强制条目。

1. 每条关键请求、会话、轮次和效果都能关联定位；记录阶段、成功/失败、已知错误类别、
   耗时，以及用户 Stop、断连、替换、关闭等取消原因。供应商真实原因未知时明确未知，
   不从 403 等单一状态臆测具体账户、计费或权限原因。
2. 用户看到稳定的安全错误码、可操作的恢复建议与诊断关联号。内部故障不把供应商
   原始异常、响应正文、路径、认证信息或用户原文暴露到界面。
3. 普通模式只保留脱敏操作元数据；本地 JSONL 日志有队列和字节上限、轮转、私有权限
   与保留期。日志故障、磁盘慢或队列满不能阻断会话、取消和关闭。
4. 一条命令可导出重新校验过的脱敏诊断包；默认不含原始对话、模型正文、音频、环境
   文件或凭据。导出只是生成本地文件，不代表授权上传或向他人分享。
5. 开发原始录制必须单独显式开启并确认；启动于 development 环境本身不代表同意。
   开启时持续可见。原始对话、模型输入/输出、音频只有通过隐私/凭据过滤或明确内容
   隐私审核才可存入独立本地私有目录；语义审核拒绝并不等于禁止诊断复现，二者分开。
6. 即使开发模式也不能记录密钥、认证 token、Authorization 头或凭据结构。已知活动
   秘密由可信注入过滤；识别不确定、无法可靠清除的内容宁可丢弃。无法保证通用音频
   里的口述秘密自动识别或抹除；未经针对原音频的隐私审核不保存。
7. 原始录制与普通日志隔离、受容量/保留期限制、不得进入 Git 或普通导出。原始导出
   需要另一次明确操作确认；关闭模式撤销尚未开始的待写原始记录。

## 实时体验：延迟必须分阶段实测

来源：2026-10-03 用户进一步关注实时延迟。不得把音频时长、请求总耗时、响应头到达、
首个有效 PCM 包或扬声器实际出声混为同一个“首包/首声”数字。

| 验收项 | 必须记录的观察 | 当前证据边界 |
| --- | --- | --- |
| 供应商请求 | dispatch、响应头、首个验证通过的 PCM 包、流结束/取消的独立时间点 | 一次 exact Gemini3.8FlashTTS：响应头约14.77秒、完整请求约16.06秒；音频本身3.4秒。没有独立首 PCM 时间戳，TTFA未知。 |
| 实际播放 | 前端收包、首次提交到唯一播放主控、软件播放进度；人工另记真实听见的时刻/尾音 | 软件提交不证明扬声器出声；真实浏览器/设备链路仍待验收。 |
| 完整轮次 | 输入提交/结束、ASR部分与最终转写、生成、JEV审核、TTS首包与播放的关联时间线 | 各供应商单次成功不能相加成未经运行的端到端延迟。 |
| 打断与恢复 | 本地Stop生效、旧任务撤销、最后旧样本/回调、下一次输入与新输出 | 不等待服务端才能本地停止；需要真实设备尾音与新轮恢复观察。 |
